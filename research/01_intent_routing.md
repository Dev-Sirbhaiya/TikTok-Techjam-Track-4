# Intent Routing / Query Understanding for Conversational E-Commerce Search

Research pass for TikTok TechJam 2026, Track 4 "Shopping Copilot" — focused on the Buying-vs-Browsing ("Dual-Track Routing") classification problem: instantly deciding whether a turn/session should trigger a high-precision constraint-filter track or a diverse dense-retrieval exploration track.

## Overview

The "is this user buying or browsing" problem is a special case of a much older and well-studied problem: **search query intent classification**. The classic web-IR taxonomy (Broder 2002) splits intent into *navigational*, *informational*, and *transactional* ([ResearchGate summary](https://www.researchgate.net/publication/222824696_Determining_the_Informational_Navigational_and_Transactional_Intent_of_Web_Queries)). E-commerce search teams have refined this into richer, action-oriented taxonomies because a binary label isn't enough to drive system *behavior* — the taxonomy has to map directly onto retrieval/ranking/filtering decisions, not just describe the query.

Two framings recur across the literature and are both directly relevant to our two-track design:

1. **Behavioral/log-based taxonomies** (older IR literature): *target finding*, *decision making*, *exploration* as three goal types with distinct query/click/browse patterns; a related clustering-based taxonomy yields *shallow exploration, major-item shopping, targeted purchase, minor-item shopping, hard-choice shopping* (via [arXiv:2005.13808](https://arxiv.org/pdf/2005.13808), User Intent Inference for Web Search and Conversational Agents).
2. **Operational/production taxonomies** (industry engineering blogs): e.g. Wizzy's six-way split — *Lookup/Known-Item, Constraint-Driven, Substitution, Problem-Solution, Exploratory/Discovery, Abandonment Retargeting* — each mapped to a specific retrieval/ranking behavior ([Search Query Classification for Ecommerce](https://wizzy.ai/blog/search-query-classification-for-ecommerce-models-signals-failure-modes/)). Their framing is the single most useful sentence found in this research: *"Query classification does not exist to answer the question 'What kind of query is this?' It exists to answer 'How should search behave for this query?'"* This is exactly our situation — Buying vs. Browsing is not an academic label, it's a dispatch decision between two concrete retrieval pipelines.

Our "Buying" track corresponds most closely to their *Constraint-Driven* / *Lookup* classes; "Browsing" corresponds to *Exploratory/Discovery* (with *Substitution* and *Problem-Solution* as harder middle cases that a real system would need to route carefully, likely toward the dense/browsing track with constraint-soft-boosting rather than hard filters).

Modern conversational commerce complicates this further because intent is not a property of one query — it accumulates and can drift across turns. This is treated in both conversational-recommender-system (CRS) literature and in very recent (2026) LLM multi-turn-dialogue research on "intent lock-in" and drift (see Failure Modes below).

## Key approaches found

### 1. Classical query classification (rules → ML → embeddings → hybrid)
Wizzy's engineering writeup lays out the standard evolution path used in production e-commerce search stacks ([source](https://wizzy.ai/blog/search-query-classification-for-ecommerce-models-signals-failure-modes/)):
- **Rule-based**: pattern/keyword matchers, price-token regex, brand gazetteers. Predictable, auditable, cheap, but brittle to phrasing variance.
- **Statistical/ML classifiers**: logistic regression / gradient boosting over lexical + behavioral features. Scales, handles the "medium confidence" middle, but needs labeled training data and struggles cold-start.
- **Embedding-based / semantic**: classify by nearest-neighbor similarity to intent exemplars in vector space. Language-aware, generalizes to paraphrase, but risks over-generalizing distinct fine-grained intents together.
- **Hybrid** (most mature systems): rules as a safety net / hard override, learned or embedding models for the ambiguous middle. This is the pattern most compatible with our no-training constraint.

Signals combined (per the same source): **linguistic** (explicit modifiers like "under", "for", exact SKU/brand tokens), **semantic** (closeness to known-category language vs. generic language), **behavioral** (click/dwell/refinement patterns — not available to us pre-launch since sessions are simulated/labeled, but *could* be approximated from within-session turn history), and **contextual** (prior filters set earlier in the session, entry point).

### 2. Embedding-based "semantic routing" (no LLM call, no training)
[`aurelio-labs/semantic-router`](https://github.com/aurelio-labs/semantic-router) is a widely used open-source library that implements exactly the "cheap runtime routing" pattern we need: define each route (e.g. "Buying", "Browsing") as a small set of seed utterances, embed them once, and at runtime embed the incoming turn and route by nearest-neighbor / cosine similarity against route centroids. No LLM generation call, no gradient training — just an embedding model (can be small and local, e.g. a HuggingFace encoder) plus a similarity threshold. This is directly transferable to our in-memory, no-training constraint: we'd hand-write ~10-20 exemplar buying utterances ("I want the blue Nike running shoes size 10 under $80") and ~10-20 browsing exemplars ("I'm looking for something for a summer wedding", "show me trendy streetwear ideas") and route new turns/accumulated session state against both clusters.

### 3. LLM-based zero-shot / few-shot intent classification with structured output
Multiple sources converge on the same modern pattern: use a small, fast LLM call with a **function-calling / structured-output schema** (e.g., `{"track": "buying"|"browsing", "confidence": float, "constraints": {...}}`) rather than free-text generation, which keeps latency and cost low while retaining LLM-level language understanding for phrasing the rule-based/embedding approaches would miss ([Intent Classification With LLMs guide](https://www.respan.ai/articles/intent-classification-with-llms); [NVIDIA AIQ Blueprint Intent Classifier](https://docs.nvidia.com/aiq-blueprint/2.0.0/architecture/agents/intent-classifier.html), which explicitly combines classification + routing + a meta-response in *one* LLM call to minimize round trips). Academic work on zero/few-shot intent detection ([ACL 2023 industry track](https://aclanthology.org/2023.acl-industry.71.pdf), [arXiv:2305.07157](https://arxiv.org/pdf/2305.07157)) confirms LLM zero-shot classification is competitive with trained classifiers on intent taxonomies of this size (2-10 classes), which matches our binary/few-way routing need.

For **multi-turn** intent classification specifically, LARA ([arXiv:2403.16504](https://arxiv.org/html/2403.16504v1)) proposes zero-shot in-context learning with single-turn demonstrations plus a crafted instruction prompt that folds conversation history into the classification prompt without needing a trained multi-turn model — again directly compatible with a no-training, in-memory constraint.

### 4. Constraint extraction / slot-filling as the "Buying" signal detector
The Buying track's job isn't just "yes/no" — it's identifying *which hard constraints* to lock. This is the well-studied **slot-filling** problem in e-commerce NLU:
- Alibaba's production system splits query tokens into **Category (CG)**, **Property Key (PK)**, **Property Value (PV)** ("brand" = PK, "Nike" = PV, "shoes" = CG) — see [Alibaba Tech: Syntax Before Semantics slot-filling model](https://medium.com/@alitech_2017/syntax-before-semantics-a-new-slot-filling-model-for-online-shopping-assistants-92e7ea3f1b17).
- Distant-supervision slot-filling for e-commerce queries ([arXiv:2012.08134](https://arxiv.org/pdf/2012.08134)) — relevant for cheaply bootstrapping slot patterns from catalog attribute values without hand-labeling, though this requires an offline pass over the catalog (permissible: catalog is read-only, not off-limits to read).
- Zero-shot slot filling with LLMs ([arXiv:2411.18980](https://arxiv.org/pdf/2411.18980)) shows LLMs can do this extraction directly without a trained slot-tagger, again matching the no-training constraint.
- A directly-relevant applied paper: **"LLM-based Semantic Search for Conversational Queries in E-commerce"** ([arXiv:2601.16492](https://arxiv.org/html/2601.16492v1)) implements almost exactly our target architecture: (1) extract structured constraints (price, rating, subcategory) from the conversational query into JSON, (2) apply them as a hard FAISS ID-filter pre-selection step, (3) rank the filtered survivors by dense embedding similarity. They report 99.4% constraint-extraction match accuracy. The one thing that doesn't transfer directly is that they *fine-tuned* a Flan-T5-small extractor and a sentence encoder — under our no-training constraint the equivalent would be a zero-shot LLM-prompt extractor (or regex/gazetteer over known catalog attribute values) feeding the same filter-then-rank pipeline. The **two-stage filter→rank architecture itself is the transferable insight**, independent of how the extractor was built.

### 5. Hybrid sparse+dense retrieval as the mechanism behind the two tracks
Multiple sources on hybrid search (Weaviate, Meilisearch, general RAG blogs) converge on: sparse/BM25-style lexical matching is best for exact-term intent (SKUs, brand names, exact category words), dense embeddings are best for semantic/exploratory intent, and production systems typically fuse both via Reciprocal Rank Fusion (RRF) rather than choosing one exclusively ([Weaviate: Hybrid Search Explained](https://weaviate.io/blog/hybrid-search-explained); [digitalapplied.com BM25/Vector/Reranking reference](https://www.digitalapplied.com/blog/hybrid-search-bm25-vector-reranking-reference-2026)). This validates the *shape* of Dual-Track Routing conceptually (hard-filter/lexical for Buying, dense for Browsing) — but it's usually framed as "run both, fuse the results" rather than "pick one track and commit," which is a meaningfully different design point worth weighing (see Recommended Approaches).

Elastic's engineering blog on **query-time policy resolution** is a close industrial analogue to "lock hard constraints": hard constraints are implemented as `bool.filter` clauses (exclude non-matches entirely, no scoring impact) while soft preferences are implemented as `function_score` boosts (influence ranking without exclusion) ([Elastic Search Labs: Resolving policy conflicts at query time](https://www.elastic.co/search-labs/blog/ecommerce-search-governance-control-plane-architecture)). This filter-vs-boost distinction is the cleanest operational definition of "hard constraint" we found and maps directly onto what "locking" brand/size/price/category should mean mechanically in our system, regardless of retrieval backend.

### 6. Real-world conversational shopping assistants
- **Amazon Rufus**: uses a real-time query-planner/router that dispatches to different backing models (Claude, Nova, custom store-knowledge model) depending on query type, and layers RAG over multiple evidence sources (catalog, reviews, Q&A, external editorial content) on top of a knowledge graph for "semantic probability" product matching ([dejan.ai: Rufus Under the Hood](https://dejan.ai/blog/rufus/); [Amazon Science: technology behind Rufus](https://www.amazon.science/blog/the-technology-behind-amazons-genai-powered-shopping-assistant-rufus)). Confirms that even at Amazon's scale, "route first, retrieve differently per route" is the chosen architecture, not a single unified retriever.
- **ShoppingGPT** ([GitHub: Hoanganhvu123/ShoppingGPT](https://github.com/Hoanganhvu123/ShoppingGPT)) — an open-source RAG + LLM shopping assistant that explicitly uses a "Semantic Router" component to dispatch queries, i.e., a hobbyist/hackathon-scale implementation of the same embedding-routing pattern as `semantic-router`.
- **ShopMind** (Kasparro Hackathon 2026 entry, [GitHub: adyapathak22/shopmind-agent](https://github.com/adyapathak22/shopmind-agent)) — conversational agent that replaces browse/search/filter with natural-language interaction plus clarifying questions before retrieving from Shopify; evidence that "ask a clarifying question when intent is underspecified" is a common hackathon-grade pattern, relevant to our turn-budget tradeoff.
- **ShoppingBench** ([arXiv:2508.04266](https://arxiv.org/abs/2508.04266)) is an AAAI 2026 benchmark for LLM shopping agents with a 4-way intent taxonomy of increasing complexity (Products Finder, Knowledge, Multi-product-seller, Coupon & Budget) and reports that even GPT-4.1-class agents score under 50% success — a useful calibration point that even strong LLM agents struggle with grounded shopping intent, reinforcing that our system should not over-rely on single-shot LLM judgment without a validation/fallback layer.

### 7. Clarifying questions as an alternative/complement to hard routing
Rather than routing binarily, conversational-IR research treats **asking a clarifying question** as a first-class system action when intent confidence is low ([Zero-shot Clarifying Question Generation for Conversational Search, Microsoft Research / SIGIR 2023](https://arxiv.org/abs/2301.12660); [CIKM 2023: Generating Intent-aware Clarifying Questions](https://dl.acm.org/doi/10.1145/3627673.3679851)). The literature explicitly frames this as a **turn-budget tradeoff**: clarification improves precision but costs a turn, so systems use "budgeted turns" or "cost-sensitive stopping" criteria. This is highly relevant given our hard 10-turn cap and the fact that MTTC (mean turns to conversion) is a scored metric — every clarifying turn has a direct, measured cost.

## Relevance to our constraints

| Constraint | Implication for intent routing design |
|---|---|
| **Max 10 turns / hard fail if exceeded** | Routing decisions must be made in ≤1 extra "thinking" step per turn — no multi-round clarification loops as a default strategy. Confidence-gated single clarifying question is acceptable per the clarifying-question literature, but should be used sparingly (e.g., only under real ambiguity, not as a default first turn), since each clarification burns from the same 10-turn budget that MTTC is scored against. |
| **Catalog read-only, in-memory only** | Rules/gazetteers for constraint values (brand list, size vocabulary, category names) can be *derived once, offline, from the catalog itself* (a read scan, not a write) and held in memory as lookup sets — this is a zero-training way to get high-precision slot detectors for the Buying track, directly inspired by the Alibaba CG/PK/PV slot scheme and distant-supervision slot-filling approach above. No vector DB cluster is implied by "semantic routing" — a small in-process embedding model (or even a handful of precomputed route-centroid vectors) is fully consistent with "in-memory." |
| **No training/fine-tuning of foundation models** | Rules out the arXiv:2601.16492 paper's literal implementation (fine-tuned Flan-T5 + fine-tuned sentence encoder), but not its *architecture* (extract constraints → filter → dense-rank). Zero-shot LLM prompting (function-calling/structured-output) or embedding-nearest-neighbor routing (`semantic-router`-style, using an off-the-shelf pretrained encoder with hand-authored exemplars) both satisfy "no training" while achieving the same architectural pattern. |
| **Text-only** | All the approaches surveyed are text-only natively; no relevant technique here depended on multimodal signals, so no adaptation needed. |
| **No UI, headless API** | Behavioral signals (dwell time, click patterns) used by some production classifiers (Wizzy) are not available to us — we only have the text of the turns and accumulated session state. This pushes us toward the linguistic + semantic + dialogue-context signal types, not behavioral ones. |
| **Evaluated on Hit Rate@K, MRR, MTTC** | Over-triggering the strict filter track kills Hit Rate/coverage (per Wizzy's "Over-Strict Constraint Enforcement" and "Exploratory-as-Lookup Misclassification" failure modes — zero-result or too-narrow result sets). Under-triggering it (staying in browsing/dense mode when the user actually gave hard constraints) hurts MRR/precision because correct-but-diverse results rank lower than a tightly filtered correct answer. MTTC rewards resolving intent in fewer turns, which argues against defaulting to clarifying questions and toward confident single-turn routing wherever signal is clear, reserving clarification for genuinely low-confidence cases. |

## Recommended approach(es), ranked

**1. (Recommended) Hybrid rule/gazetteer + lightweight embedding router, LLM as fallback/arbiter only on low confidence.**
- Build, once, at startup, from the frozen catalog: in-memory sets/tries of brand names, size tokens, category names, color vocabulary, and a price-token regex (currency + number + comparator words like "under/below/less than/max"). This gives near-zero-latency, high-precision detection of explicit hard-constraint mentions ("Nike", "size 10", "under $50") — the strongest, cheapest signal for Buying intent, and directly grounded in the catalog so it can't hallucinate a brand/category that doesn't exist.
- In parallel, maintain a small set of hand-authored exemplar utterances for "Buying" vs. "Browsing" phrasing style (independent of whether explicit slot values are present — e.g., "I need X now" vs. "give me some ideas for X"), embed them once with an off-the-shelf sentence encoder, and route each turn (or the accumulated session utterance) by cosine similarity to the two exemplar clusters — the `semantic-router` pattern. This catches intent expressed in *phrasing* even when no hard slot value is present yet (e.g. "I want to buy running shoes" has no brand/size but is clearly transactional).
- Combine: if the gazetteer finds ≥1 hard-constraint slot with reasonable confidence, route Buying and lock exactly the slots found (don't invent ones not mentioned — avoids the "over-strict" failure mode). If no slot is found, fall back to the embedding-similarity vote. Only call an LLM (zero-shot structured-output classification, one call, cheap model) when both signals disagree or both are low-confidence — keeping the expensive path rare and reserved for genuinely ambiguous turns.
- *Rationale*: This is the cheapest possible design (no network/model call on the common path), fully in-memory, needs zero training, is auditable/debuggable (you can always explain "why did it route Buying" by pointing at the matched slot or exemplar), and matches how mature production systems are described (Wizzy's "hybrid: rules for safety, learned/embedding models for the ambiguous middle").

**2. Single structured-output LLM call per turn, session-state-aware.**
- Every turn, issue one LLM call with a compact prompt containing the running session state (accumulated slots, prior track) and the new utterance, asking for structured JSON: `{track, confidence, new_constraints, constraints_to_relax}`. Use function-calling/schema-constrained decoding so it's cheap and parseable (per Respan/NVIDIA AIQ pattern).
- *Rationale*: Simpler to build than option 1, handles novel phrasing well, and naturally supports the "accumulated dialogue" requirement since it can be fed the whole session transcript each turn (transcripts are short — max 10 turns). Downside: adds one LLM round-trip of latency per turn on the *entire* traffic, not just ambiguous cases, which is wasteful given option 1 can resolve most turns for free; also introduces LLM-classification error risk on every turn (ShoppingBench shows even strong LLMs are inconsistent on grounded shopping intent) rather than only on the hard cases. Recommended only if implementation time is very tight and a single, simpler code path is preferred over building the gazetteer.

**3. Confidence-gated clarifying question as an explicit third routing outcome (used sparingly, layered on top of option 1 or 2).**
- Add a third outcome besides {Buying, Browsing}: "Ambiguous → ask one targeted clarifying question" (e.g., "Are you looking for something specific, or exploring ideas?" / "What's your budget?"), but cap this to at most once per session, and only trigger when confidence from the primary router is near the decision boundary.
- *Rationale*: Matches the literature's "budgeted clarification" pattern and can improve MRR/Hit Rate on genuinely ambiguous openers ("I need something nice") without regularly costing a turn, since MTTC penalizes turns spent — this should be the exception path, not a default first move, and should never be used more than once given the 10-turn ceiling.

## Dos

- **Do** derive slot vocabularies (brands, sizes, colors, categories, price patterns) from the actual frozen catalog at load time — it's free, in-memory, grounded, and prevents hallucinated constraints.
- **Do** treat hard constraints as *filters that exclude* and soft/exploratory signals as *boosts that reorder without excluding* — this filter-vs-boost distinction (Elastic's pattern) is the cleanest mechanical definition of "locking" a constraint.
- **Do** make routing decisions primarily from cheap, deterministic signals (regex/gazetteer/embedding similarity) and reserve any LLM call for the ambiguous minority of turns, to control latency and cost given the turn budget.
- **Do** carry constraints across turns as accumulated session state rather than re-deriving from a single utterance each time — buying intent is often established over 2-3 turns, not a single message.
- **Do** allow constraints to be *relaxed* explicitly if the user's later turn signals a category/attribute change (e.g., "actually let's look at something cheaper") — treat this as a legitimate track-relevant update, not noise.
- **Do** log/expose which slot or exemplar triggered a routing decision (interpretability), since debugging misroutes quickly is critical under a hard 10-turn eval budget.
- **Do** calibrate thresholds (for embedding similarity or LLM confidence) against the 200 labeled dev sessions before finalizing — thresholds tuned on a different domain's exemplars will likely misfire.

## Don'ts

- **Don't** default to a single LLM classification call on every turn if a cheaper deterministic signal already resolves it confidently — unnecessary latency/cost against a hard turn budget.
- **Don't** treat every mentioned attribute as a hard filter automatically — per Wizzy's "Over-Strict Constraint Enforcement" failure mode, promoting a soft preference (style, general vibe) to a hard filter causes zero-result dead ends that tank Hit Rate.
- **Don't** classify once at session start and freeze the track for all 10 turns — per the CRS literature and the "classification oscillation" failure mode, intent legitimately shifts mid-session (browsing → converges on a specific item, or vice versa); re-evaluate lightly every turn using accumulated state, not just the latest utterance in isolation.
- **Don't** rely on behavioral signals (clicks, dwell time) that don't exist in this headless, session-based, text-only evaluation setting — only linguistic, semantic, and dialogue-context signals are available.
- **Don't** use unlimited or repeated clarifying questions as a crutch for classifier uncertainty — each one consumes turn budget that directly hurts MTTC, and the 10-turn hard fail makes this a scored risk, not just a UX inconvenience.
- **Don't** assume model scale alone fixes multi-turn ambiguity — recent research (arXiv:2602.07338) found LLMs "lock in" early wrong interpretations of fragmented multi-turn instructions regardless of model size; the fix is explicit intent-state tracking/re-confirmation, not just a bigger model.
- **Don't** silently let the routing layer invent constraint values not present in the user's language (e.g., assuming a specific brand because it's popular) — this both breaks trust in the "locked constraint" guarantee and is a common source of over-strict/false-positive filtering.
