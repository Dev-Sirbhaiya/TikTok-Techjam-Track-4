# LLM-Based Reranking / Semantic Ranking for Product Search & Conversational Recommendation

Research for TikTok TechJam 2026 Track 4 ("Shopping Copilot"): the pipeline's "LLM Semantic Ranking" stage, which must push the true purchased item to rank 1 as often as possible (MRR / Top-K Hit Rate) while respecting a 10-turn conversational budget, no fine-tuning, no guaranteed paid LLM API, and in-memory-only infra.

## Overview

Reranking sits between broad "multi-route retrieval" (recall-oriented: BM25/lexical, dense/embedding, metadata/filter routes) and the final answer, narrowing a candidate pool (typically top-20 to top-100 from retrieval) down to a precisely ordered top-K. The field has converged on three LLM-native ranking paradigms — **pointwise, pairwise, listwise** — plus a mature, much cheaper alternative family of **cross-encoder / late-interaction rerankers** that need no LLM API at all. The central production tension documented everywhere: LLM-based rerankers (especially listwise) give the best relevance-judgment quality but at order(s)-of-magnitude higher latency/cost than a small trained cross-encoder, and several recent 2025-2026 benchmarks report that a *calibrated cross-encoder actually beats general-purpose LLM rerankers* on NDCG while being ~100-1000x cheaper (ZeroEntropy 2026 benchmark). This directly matters for a hackathon under a hard turn budget with no promised API key: the practical answer is a **staged/hybrid pipeline** — cheap fusion + cross-encoder does the heavy lifting on every turn, with an optional LLM listwise pass reserved for a tiny top-N (5-10) when an API key is available, or skipped/replaced entirely on the non-paid fallback path.

## Key approaches found (with inline citations/links)

### 1. LLM ranking paradigms

- **Pointwise scoring** — the LLM (or a prompted scoring function) assigns an independent relevance score/label to each (query, candidate) pair; candidates are then sorted by score. Simple to implement and trivially parallelizable/batchable, but requires one call per candidate (or a batched multi-item prompt), does not capture *relative* preference between candidates, and LLM-generated pointwise scores are frequently uncalibrated across queries. Benchmarks show pointwise LLM scoring is generally the *worst* value proposition: "pointwise LLM reranking is almost never worth it — 10x the cost and lower accuracy than specialized rerankers," and at ~100 candidates/query it needs dozens of sequential calls, "15+ seconds end-to-end" even with a fast model. ([ZeroEntropy: Should you use LLMs for reranking](https://zeroentropy.dev/articles/should-you-use-llms-for-reranking-a-deep-dive-into-pointwise-listwise-and-cross-encoders/), [ZeroEntropy: LLM-as-reranker guide](https://zeroentropy.dev/articles/llm-as-reranker-guide/), [EmergentMind: Pointwise Generative Ranking](https://www.emergentmind.com/topics/pointwise-generative-ranking))
- **Pairwise comparison** — the LLM is asked "which of A, B is more relevant" and comparisons are aggregated (e.g., via a sorting network or Elo-style rating) into a full ranking. More robust per-judgment than pointwise (relative judgments are easier for LLMs than absolute scores) but needs O(K log K) to O(K²) comparisons, making it the *most* expensive paradigm at scale. ZeroEntropy's production reranker (zerank-1) uses pairwise preferences converted to Elo-style calibrated scores specifically because pairwise judgments are more stable/comparable across queries than pointwise absolute scores. ([ZeroEntropy pointwise/listwise/cross-encoder deep dive](https://zeroentropy.dev/articles/should-you-use-llms-for-reranking-a-deep-dive-into-pointwise-listwise-and-cross-encoders/))
- **Listwise ranking (RankGPT-style)** — the LLM sees the *entire* candidate list in one prompt and directly outputs a permutation (ranked list of candidate IDs), rather than independent scores. This is the paradigm introduced by **RankGPT** / "Is ChatGPT Good at Search? Investigating LLMs as Re-Ranking Agents" (Sun et al., EMNLP 2023 Outstanding Paper), which proposes "instructional permutation generation": the LLM emits an ordering like `[2] > [3] > [1] > ...` for a window of candidates. Because prompt/context limits cap how many candidates fit at once, RankGPT uses a **sliding window** (e.g. window_size=20, step=10) scanning back-to-front so more than the context-window's worth of candidates (e.g. 100) can still be fully reranked through repeated partial permutations. ([arXiv:2304.09542](https://arxiv.org/html/2304.09542v3), [GitHub: sunnweiwei/RankGPT](https://github.com/sunnweiwei/RankGPT), [DataCamp RankGPT tutorial](https://www.datacamp.com/tutorial/rankgpt-rag-reranking-agent))
  - Distilled open-weight listwise rerankers followed: **RankVicuna** (7B, distilled from RankGPT-3.5 output, trained with shuffled inputs for order robustness) and **RankZephyr** (7B, fine-tuned on RankGPT-4 outputs, supports multiple reranking passes for stronger accuracy) bring listwise quality to self-hostable open models, removing the need for a paid API. ([arXiv:2309.15088 RankVicuna](https://arxiv.org/pdf/2309.15088), [arXiv:2312.02724 RankZephyr](https://arxiv.org/html/2312.02724v1))
  - Latency is real: RankVicuna/RankZephyr take **~13.8s and ~14.9s respectively to rerank 50 documents on a V100 GPU** — too slow, as-is, for a hard per-turn budget unless the candidate set fed to them is cut drastically. Follow-on work like **FIRST** (single-token decoding for listwise reranking) cuts inference time by **21-42%** across RankZephyr/RankVicuna/RankMistral by having the model emit a single relevance-ordering token per step instead of full generation. ([arXiv:2411.05508 FIRST](https://arxiv.org/html/2411.05508v1))
  - Follow-up analyses: **Rank-without-GPT** (building GPT-independent listwise rerankers on open LLMs, [arXiv:2312.02969](https://arxiv.org/html/2312.02969v1)); **RankFlow** (multi-role collaborative LLM reranking workflow, [arXiv:2502.00709](https://arxiv.org/pdf/2502.00709)); a 2025 EMNLP Findings empirical study "How Good are LLM-based Rerankers?" benchmarking pointwise/listwise LLM rerankers against cross-encoders at scale ([arXiv:2508.16757](https://arxiv.org/pdf/2508.16757), [ACL Anthology](https://aclanthology.org/2025.findings-emnlp.305.pdf)); and "Efficiency-Effectiveness Reranking FLOPs for LLM-based Rerankers" which formalizes the compute-cost side of this tradeoff ([arXiv:2507.06223](https://arxiv.org/html/2507.06223)).
  - **RankLLM / rank_llm** (Castorini, University of Waterloo) is a reproducible research toolkit bundling RankGPT, RankVicuna, RankZephyr and other listwise rerankers behind a common interface — the most citable "prior art" codebase for listwise LLM reranking. ([GitHub: castorini/rank_llm](https://github.com/castorini/rank_llm/))

- **Head-to-head verdict from a 2026 practitioner benchmark (ZeroEntropy, 17 IR datasets):** pointwise general LLM (GPT-5-mini) scores 0.70 NDCG@10 at ~2180ms p50 and ~10x the cost of a dedicated reranker; listwise LLM (GPT-5-nano) is only marginally better, ~1520ms p50, ~2x cross-encoder cost, and "only viable for very small candidate sets" due to quadratic attention cost and token limits; a trained cross-encoder (zerank-1) scores **0.78 NDCG@10 at 130ms p50**, beating both LLM approaches on quality *and* being 10-15x faster and far cheaper. Their recommended layered strategy: **first-stage lexical/embedding recall → cross-encoder rerank on top 50-100 → optional LLM listwise pass on only the top 5-10.** ([ZeroEntropy deep-dive](https://zeroentropy.dev/articles/should-you-use-llms-for-reranking-a-deep-dive-into-pointwise-listwise-and-cross-encoders/), [ZeroEntropy ultimate guide 2026](https://zeroentropy.dev/articles/ultimate-guide-to-choosing-the-best-reranking-model-in-2025/))
- On the **Amazon ESCI** shopping-queries benchmark specifically, a staged architecture study reports each added stage contributes incrementally: BM25 → HNSW dense (+3.1pp NDCG@5) → Hybrid RRF (+2.4pp) → Cross-encoder (+2.4pp) → **LLM reranker (+4.8pp)** — i.e., the LLM stage gives the single largest marginal jump, but only after cheaper stages have already narrowed and cleaned the pool. This validates a multi-stage funnel design for our own pipeline. ([code-mixed-search-benchmark technical report](https://github.com/tanmay0401/code-mixed-search-benchmark/blob/main/reports/technical_report.md), [Amazon ESCI dataset](https://github.com/amazon-science/esci-data), [arXiv:2206.06588](https://arxiv.org/abs/2206.06588))

### 2. Cross-encoder / non-LLM-API rerankers (the no-paid-API answer)

- **`ms-marco-MiniLM-L-6-v2` / `-L-12-v2`** (sentence-transformers): the most widely used open cross-encoder, 6-12 transformer layers, 512-token max sequence, trained on MS MARCO; extremely fast, CPU-friendly, no API key. ([OpenSearch tutorial](https://docs.opensearch.org/latest/tutorials/reranking/reranking-cross-encoder/))
- **BGE-reranker (`bge-reranker-base/large/v2-m3`)**: stronger multilingual cross-encoder family from BAAI; v2-m3 is noticeably more accurate but **~10.6x slower** than ms-marco-MiniLM (~1.1s to score 1000 candidates) — fine if only scoring a narrowed shortlist, not the full retrieval pool. ([arXiv:2604.15484](https://arxiv.org/pdf/2604.15484))
- **ColBERT / late-interaction models (ColBERTv2, PLAID)**: instead of a single relevance score, ColBERT encodes query and document into per-token vectors and scores via cheap "MaxSim" token-level interactions computed at query time, after documents are encoded and indexed *once*, offline. This decoupling gives ~2 orders-of-magnitude speedup and ~4 orders-of-magnitude fewer FLOPs/query versus full cross-attention rerankers, at competitive accuracy. **PLAID**, the optimized ColBERTv2 engine, reduces late-interaction latency by 2.5-7x (GPU) / 9-45x (CPU) versus vanilla ColBERTv2, reaching **tens to a few hundred ms end-to-end on CPU only** — attractive for an in-memory, no-GPU, no-API hackathon deployment. ([Weaviate overview](https://weaviate.io/blog/late-interaction-overview), [Qdrant late-interaction article](https://qdrant.tech/articles/late-interaction-models/), [ColBERT arXiv:2004.12832](https://arxiv.org/abs/2004.12832), [PLAID arXiv:2205.09707](https://arxiv.org/pdf/2205.09707))
- **FlashRank**: a lightweight (no PyTorch/Transformers dependency, CPU-only, "serverless-friendly") Python library bundling both cross-encoder rerankers (`ms-marco-TinyBERT-L-2-v2` ~4MB default, `ms-marco-MiniLM-L-12-v2` ~34MB, multilingual `ms-marco-MultiBERT-L-12` ~150MB, `rank-T5-flan` ~110MB) *and* a quantized listwise LLM option (`rank_zephyr_7b_v1_full`, 4-bit, ~4GB) behind one interface — a good reference implementation for "cross-encoder now, LLM later if resources allow" design. ([GitHub: PrithivirajDamodaran/FlashRank](https://github.com/PrithivirajDamodaran/FlashRank))
- **Local open-weight LLMs as rerankers via Ollama** (no API key, no internet): e.g. `dengcao/Qwen3-Reranker-4B` quantized, or general local chat models (Llama 3.2, Mistral, Gemma 2) prompted with a scoring template, wrapped behind an Ollama-compatible rerank endpoint. This is a legitimate "bring-your-own local model" fallback that still gives LLM-style multi-criteria/interpretable scoring without any paid API, at the cost of needing local compute and careful latency budgeting. ([Ollama rerank adapter](https://github.com/jtianling/dify-ollama-rerank-adapter), [Qwen3 reranker on Ollama](https://apidog.com/blog/qwen-3-embedding-reranker-ollama/), [Mem0 LLM-as-reranker docs](https://docs.mem0.ai/components/rerankers/models/llm))
- Caveat: off-the-shelf cross-encoders trained on web-search distributions (MS MARCO) can *underperform* on out-of-domain corpora (reported -0.3% to -3.1% degradation plus 560-2100ms latency in one study) — motivating a lightweight **domain-adapted scoring rule** (e.g. weighting on title/category token overlap, brand match, price-band fit) tuned via local scoring-logic tuning (allowed under the rules) rather than assuming an off-the-shelf reranker transfers perfectly to the Amazon Clothing/Shoes/Jewelry catalog. ([Towards Data Science: Rerankers Aren't Magic Either](https://towardsdatascience.com/rerankers-arent-magic-either-when-the-cross-encoder-layer-is-worth-the-cost-enterprise-document-intelligence-vol-1-2bis/))

### 3. Prompt design for e-commerce candidate representation

- General pattern across conversational-recommendation papers: prompt = **(a) compact structured candidate list** (title, key attributes/features, price, category/subcategory, rating) + **(b) accumulated dialogue state** (explicit user constraints/slots extracted so far, chronological turn history or a condensed summary) + **(c) explicit ranking instruction** (e.g. "given the user's stated preferences, output the item IDs ordered from most to least likely to be purchased"). Frameworks combining an external/candidate recommender with an LLM reranker feed "candidate items output and original dialogue history... jointly... to prompt LLMs for contextual adaptation." ([arXiv:2508.13889](https://arxiv.org/html/2508.13889), [arXiv:2507.16237 complementary product reranking](https://arxiv.org/html/2507.16237))
- Multi-agent variants split the job: an intent-extraction agent distills raw dialogue into structured slots first, then a separate reranking agent only sees the compact slot representation + candidates — this keeps the reranking prompt short across turns instead of re-feeding the full transcript each time (relevant to our 10-turn budget). E.g. "Think Then Recommend" uses a Basic Intent Extraction Agent → Detailed Intent Generation Agent → Preference-Aligned Recommendation Agent that reranks via LLM-driven intent-product alignment. ([ACM Web Conference 2026](https://dl.acm.org/doi/10.1145/3774904.3793050))
- **Context/format compression choices** that concretely affect latency and token cost:
  - Truncate product fields to the minimum needed to discriminate (short title, top 3-5 attributes, price, category, rating) rather than full description text.
  - Prefer compact **CSV/TSV/pipe-delimited or numbered-list** input formats over verbose JSON for the *input* side of the prompt — one practitioner comparison found flat delimited formats are both more token-efficient and as accurate as JSON for LLM inputs, while structured JSON is better reserved for the *output* (e.g. "return a JSON array of item IDs in ranked order") as a validated/schema-constrained target. Constrained/schema-forced JSON output reduces output tokens but showed some accuracy tradeoff vs free-form JSON generation in one study — a real design choice to test empirically. ([IBM: JSON prompting for LLMs](https://developer.ibm.com/articles/json-prompting-llms/), [MightyBot structured prompt formats](https://mightybot.ai/blog/best-structured-prompt-formats-for-llms/), [Instructor: building an LLM reranker](https://python.useinstructor.com/blog/2024/10/23/building-an-llm-based-reranker-for-your-rag-pipeline/))
  - Assign each candidate a short opaque ID (`[1]`, `[2]`, ...) for the model to output rather than repeating full titles in the ranking output — this is exactly RankGPT's permutation-generation trick and dramatically shortens the LLM's output (cuts both output tokens and error surface from the model mangling long titles).
  - Rank only the top-N from retrieval (not the whole pool) inside the prompt — see stage-4/5 below.

### 4. Score fusion: combining retrieval score + rerank rank + business signals

- **Reciprocal Rank Fusion (RRF)**: a simple, training-free, scale-independent way to combine multiple ranked lists (e.g., lexical route + dense route + metadata route, or retrieval rank + LLM rank) by summing `1/(k + rank_i)` across sources. It's popular precisely because it needs no score calibration and is robust to heterogeneous signal types — a good multi-route fusion mechanism *before* the LLM/cross-encoder stage even runs, and a good final fusion mechanism after it. A very common two-stage pattern: **RRF to fuse multi-route retrieval into one candidate pool of ~100, then cross-encoder to cut to top-10.** ([MongoDB: Better RAG results with RRF](https://www.mongodb.com/resources/basics/reciprocal-rank-fusion), [glaforge.dev RRF explainer](https://glaforge.dev/posts/2026/02/10/advanced-rag-understanding-reciprocal-rank-fusion-in-hybrid-search/), [EmergentMind RRF overview](https://www.emergentmind.com/topics/reciprocal-rank-fusion-rrf))
- **Business-signal blending**: none of the surveyed sources give one canonical formula for injecting price-fit/rating into an LLM-based rerank, but the consistent pattern across recommender-systems and search literature is a **weighted linear (or rank-fusion) blend** of: (i) retrieval/embedding similarity score, (ii) reranker score or rank, and (iii) hand-tunable business features (price-vs-stated-budget fit, star rating, review count/popularity, in-stock/availability). Two implementable variants:
  1. **Score-level fusion**: normalize each signal to [0,1] (e.g., min-max or z-score within the candidate pool) and take a weighted sum; weights are hand-tuned or grid-searched offline against the eval set (this is "local scoring-logic tuning," explicitly allowed).
  2. **Rank-level fusion (RRF variant)**: treat each signal (retrieval rank, LLM/cross-encoder rank, price-fit rank, rating rank) as its own ranked list and RRF-combine them — robust when signal scales are hard to calibrate consistently, and naturally handles the LLM's rank-only output (listwise LLMs output an order, not a calibrated score, so RRF is a more natural fit than weighted-sum fusion for that signal specifically).
  - A practical refinement is to feed price/rating/category directly into the LLM prompt itself (as candidate metadata) and let the ranking instruction explicitly ask the model to weigh stated budget and rating — collapsing "business signal fusion" into prompt design rather than a separate post-hoc formula. This is what the e-commerce reranking papers above effectively do.

### 5. Keeping LLM ranking fast across up to 10 turns

- **Rerank only top-N from retrieval, not the whole catalog.** Every source converges on this: cheap-stage recall pulls tens to ~100 candidates, expensive-stage (cross-encoder or LLM) only ever touches a small shortlist. Typical numbers cited: rerank top 20-50 down to 5-10 for the final LLM/user-facing context ([ZeroEntropy](https://zeroentropy.dev/articles/should-you-use-llms-for-reranking-a-deep-dive-into-pointwise-listwise-and-cross-encoders/); [CustomGPT RAG reranking](https://customgpt.ai/rag-reranking-techniques/)). For a 10-turn, no-guaranteed-GPU budget, an LLM (if used at all) should realistically only ever see **≤10-20 candidates per turn**, ideally in a single non-sliding-window pass (RankGPT's sliding window is for 100+ candidates and is too slow for our budget: RankZephyr/RankVicuna take ~14s to rerank just 50 docs on a V100 — cut this by cutting N, not by relying on sliding-window tricks).
- **Batching / parallel calls + prompt caching**: one applied case study reports that after "tightening the output format, enabling thresholding, adding prompt caching, and parallelizing calls, the added latency dropped to <1s" for an LLM reranking stage — i.e., cache the (mostly static) system prompt/instructions and candidate-schema boilerplate, only vary the per-turn dialogue state and candidate list, and parallelize independent scoring calls when using a pointwise or windowed approach. ([fin.ai: Using LLMs as a Reranker for RAG](https://fin.ai/research/using-llms-as-a-reranker-for-rag-a-practical-guide/))
- **Single-token / constrained decoding** (FIRST-style): forcing the reranker to emit a compact, single-token-per-item relevance signal instead of full free-text generation cuts listwise LLM inference latency 21-42% ([arXiv:2411.05508](https://arxiv.org/html/2411.05508v1)) — directly applicable if self-hosting a RankZephyr-style model.
- **Conversation-aware caching**: cache reranking results keyed on (retrieved-candidate-set, dialogue-state-slots) rather than raw last-utterance text, so that a turn which doesn't change the active filters/slots can reuse the previous turn's rerank instead of recomputing. Naive semantic caching on raw queries misfires across multi-turn context (reported false-hit issues in "ContextCache", [arXiv:2506.22791](https://arxiv.org/html/2506.22791v3)); a context-aware cache keyed on normalized dialogue state avoids this and gives ~10x lower latency on cache hits.
- **Confidence-based early exit**: skip or shortcut the expensive rerank stage when the cheap retrieval/fusion stage is already highly confident (e.g., large score gap between rank-1 and rank-2 candidate, or a very specific slot-filled query that narrows the pool to 1-3 items) — analogous to "Confidence-Based Dynamic Retrieval" and the "LLM-Confidence Reranker" pattern in RAG literature, adapted here as "skip LLM rerank, trust cross-encoder/fusion order" when the top-of-pool margin exceeds a threshold. This both saves latency budget for later turns and reduces the risk of an LLM call *demoting* an already-correct top candidate. ([arXiv:2509.06472](https://arxiv.org/html/2509.06472), [arXiv:2602.13571 LLM-Confidence Reranker](https://arxiv.org/html/2602.13571))
- **Iterative/adaptive compute-scaling**: Amazon Science's "Iterative Reranking as a Compute-Scaling Method for LLM-based Rankers" explores spending more reranking passes only when useful, rather than a fixed-depth pass every time — conceptually supports a turn-budget-aware policy (e.g., invest more rerank compute early when slots are vague, less on later turns once intent is narrow). ([Amazon Science PDF](https://cdn.amazon.science/53/7f/0bdb3680470faf1cb21f49a5998f/scipub-approval152129-43245875-iterative-reranking-as-a-computescaling-method-for-llmbased-rankers.pdf))

### 6. Prior art specific to conversational/e-commerce search

- **Amazon Shopping Queries Dataset (ESCI)** — ~130K queries, 2.6M graded (query, product) relevance judgments (Exact/Substitute/Complement/Irrelevant), the standard academic benchmark for Amazon-style product search/reranking research; directly analogous to our frozen-catalog setting. ([arXiv:2206.06588](https://arxiv.org/abs/2206.06588), [GitHub: amazon-science/esci-data](https://github.com/amazon-science/esci-data))
- **"LLM-Enhanced Reranking for Complementary Product Recommendation"** (2025) — model-agnostic LLM reranking applied as a *post-processing* layer on top of existing (e.g. GNN-based) candidate recommenders, explicitly avoiding retraining; reports ~50% lift in accuracy metrics and ~2% lift in diversity on public datasets purely from the LLM rerank layer. Strong precedent for our "no training, LLM reranks a frozen retriever's output" constraint. ([arXiv:2507.16237](https://arxiv.org/html/2507.16237))
- **"Improving Conversational Recommendation with Contextual Adaptation of External Recommenders and LLM-based Reranking"** (2025) — combines an external recommender with an LLM reranker driven jointly by candidate list + dialogue history, addressing the known failure mode where free-generation LLM recommenders hallucinate items outside the actual catalog (a critical risk for us, since the catalog is frozen and closed-world). ([arXiv:2508.13889](https://arxiv.org/html/2508.13889))
- **"Think Then Recommend"** (ACM Web Conference 2026) — multi-agent conversational recommender for e-commerce: intent-extraction agent(s) feed a preference-aligned reranking agent; a template for decoupling slot/intent tracking from the reranking prompt itself, keeping the rerank prompt short turn-over-turn. ([ACM DL](https://dl.acm.org/doi/10.1145/3774904.3793050))
- **"Prompt-Based LLMs for Position Bias-Aware Reranking in Personalized Recommendations"** — addresses the well-known LLM listwise bias toward favoring items placed early/late in the input list (position bias), relevant if we adopt listwise prompting: mitigations include randomizing/shuffling candidate order across repeated calls and aggregating, or explicit debiasing instructions. ([arXiv:2505.04948](https://arxiv.org/pdf/2505.04948))
- **RankLLM / rank_llm** (Castorini) is the most reusable open codebase implementing RankGPT/RankVicuna/RankZephyr-style listwise reranking end-to-end; **FlashRank** is the most reusable open codebase for the cheap cross-encoder + optional small-listwise-LLM path with zero GPU/API dependency. Both are directly adoptable (not necessarily verbatim, but as reference implementations) for our two candidate architectures (LLM-available vs. no-paid-API fallback). ([castorini/rank_llm](https://github.com/castorini/rank_llm/), [PrithivirajDamodaran/FlashRank](https://github.com/PrithivirajDamodaran/FlashRank))
- Survey aggregators worth mining further if time allows: **awesome-rerankers** ([agentset-ai/awesome-rerankers](https://github.com/agentset-ai/awesome-rerankers)), **Awesome-LLM-for-RecSys** ([CHIANGEL/Awesome-LLM-for-RecSys](https://github.com/CHIANGEL/Awesome-LLM-for-RecSys)), **LLMSearchRecommender** compendium ([alopatenko/LLMSearchRecommender](https://github.com/alopatenko/LLMSearchRecommender)), and **reranker-eval** benchmarking harness ([agentset-ai/reranker-eval](https://github.com/agentset-ai/reranker-eval)).

## Relevance to our constraints (10-turn latency, no training, no guaranteed paid LLM API, MRR-focused eval)

- **No training/fine-tuning allowed** rules out RankVicuna/RankZephyr-style *distillation* as something we'd build ourselves, but not as something we *use* off-the-shelf (they're pre-trained, zero-shot-usable open weights) — legitimate if self-hosting is feasible. "Local scoring-logic tuning" (allowed) covers hand-tuning fusion weights, price-fit heuristics, and prompt engineering — which is exactly where most of the achievable MRR gain lives per the evidence above (prompt design + fusion, not model training).
- **Hard 10-turn budget with a heavy MTTC penalty** means per-turn rerank latency must be small and *predictable*. Full listwise LLM reranking at 50 candidates (~14s) is disqualifying; either shrink N drastically (≤10-15 candidates) for a single-pass listwise prompt, use pointwise/batched scoring with parallel calls, or default to a cross-encoder (~100-200ms) with the LLM only as an occasional/optional refinement — not a per-turn requirement.
- **No guaranteed paid LLM API** is the most consequential constraint: it means the reranking stage's default/baseline implementation *cannot assume an LLM call succeeds or is affordable*. The literature gives us a clean, well-precedented non-LLM fallback (cross-encoder or ColBERT-style late interaction) that is CPU-only, sub-200ms, and reportedly *competitive with or better than* general LLM rerankers on standard IR metrics — this de-risks the whole track-4 requirement rather than being a compromise.
- **MRR / Top-K on pushing the exact purchased item to rank 1** rewards precision at the very top far more than broad relevance ordering — this favors (a) a strong first-pass retrieval + fusion that reliably gets the true item into the shortlist (recall gate), and (b) a reranking scorer with good top-1 discrimination (calibrated cross-encoder or a tightly-prompted single-pass listwise LLM on a short list) over paradigms that spend budget refining the middle/tail of the ranking (e.g., large-K listwise sliding windows, exhaustive pairwise tournaments) that a 10-turn/no-training/no-guaranteed-API setup can't afford anyway.
- **In-memory-only, no external vector DB clusters** rules out heavyweight ColBERT/PLAID production deployments that assume a dedicated ANN index service, but a lightweight in-process ColBERT-style scorer or a simple cross-encoder over an in-memory shortlist is fully compatible — the "in-memory" constraint mainly disqualifies external clustered infra, not the reranker's compute pattern itself.

## Recommended approach(es), ranked, with rationale

1. **Primary recommendation — tiered pipeline with cross-encoder as the guaranteed stage and LLM listwise rerank as an optional booster:**
   Multi-route retrieval/fusion (RRF across lexical + embedding + metadata routes) → narrow to ~30-50 candidates → **cross-encoder rerank** (e.g. `ms-marco-MiniLM-L-6-v2` or FlashRank's default TinyBERT for speed, or `bge-reranker-base` if a small accuracy bump is worth ~10x latency on a *short* list) narrows to top 8-12 → **if** an LLM (local or API) is available and turn-latency budget allows, run a **single-pass listwise LLM rerank** (no sliding window — list is already short) on just those 8-12 candidates, output a simple `[id, id, id, ...]` permutation, then rank-fuse the LLM permutation with the cross-encoder rank and business-signal ranks (price-fit, rating) via RRF or a hand-tuned weighted blend. This directly mirrors the staged-funnel design validated on ESCI (BM25→dense→RRF→cross-encoder→LLM, each stage adding measurable NDCG) and matches the "always apply the most expensive technique to the smallest candidate count" principle repeated across every source reviewed.
   *Rationale:* guarantees a fast, dependency-free baseline (cross-encoder path always works, no API key needed) while still capturing the LLM stage's demonstrated largest marginal MRR/NDCG gain when a model is available — satisfying the track's explicit requirement for an "LLM Semantic Ranking" stage without making the whole pipeline fragile to API availability.

2. **No-paid-API fallback (should be the default assumption, not an afterthought):**
   Skip the LLM call entirely; use the cross-encoder (or ColBERT-style late-interaction scorer if embeddings are already being computed for retrieval) as the sole "semantic ranking" stage, fused with business signals via RRF/weighted blend. Optionally simulate "LLM-like" scoring with a small local model via Ollama (e.g. a quantized Qwen3-Reranker or a general small chat model prompted with a strict scoring template) if local compute is available and adds measurable MRR without blowing the latency budget — this still counts as an "LLM-like scoring" stage per the track's own allowance for local scoring-logic tuning, while remaining fully offline and free.
   *Rationale:* removes single point of failure; every documented practitioner benchmark found the cross-encoder path to be strong on its own (0.78 NDCG@10 vs 0.70-0.74 for general-purpose LLM rerankers in one head-to-head), so this is not merely a "worse but safe" option — it may be the stronger choice outright for this workload.

3. **If pursuing the LLM path, prefer listwise-single-pass over pointwise or pairwise:**
   Given the 10-turn budget, pointwise (many sequential/parallel calls per turn) and pairwise (O(K log K) comparisons) both burn more calls than a single listwise pass over an already-short (≤12) candidate list. Use RankGPT-style permutation-instruction prompting (opaque numeric IDs, minimal fields) but skip the sliding-window machinery entirely since N is small — this captures RankGPT's core technique without its main latency cost driver.

4. **Score fusion:** use RRF as the default fusion mechanism across heterogeneous signal types (retrieval score, cross-encoder rank, LLM permutation rank, price-fit rank, rating rank) since it needs no calibration and is robust/training-free; optionally hand-tune RRF's `k` constant or add signal weights against the eval set (permitted "local scoring-logic tuning").

5. **Latency safety nets regardless of path chosen:** cap candidate pool size hard before any expensive stage; cache per-turn rerank results keyed on normalized dialogue-state/slots (not raw text) so unchanged turns skip recomputation; add a confidence-gated early exit that trusts the cross-encoder/fusion order outright when its top-1/top-2 score margin is large, reserving the LLM call's latency budget for turns where the ranking is genuinely ambiguous.

## Dos

- Do run retrieval/fusion recall-oriented and reranking precision-oriented — keep them as separate stages with the reranker only ever touching a small shortlist (≤10-50 candidates, ideally ≤15 if an LLM is in the loop).
- Do default to a cross-encoder (or ColBERT-style late interaction) as the guaranteed, no-API, in-memory-friendly reranking stage, and treat any LLM call as an optional enhancement layered on top.
- Do use opaque short IDs for candidates in LLM prompts and request a simple ordered-ID-list output rather than re-emitting full titles — shortens both prompt and completion, and reduces parsing/hallucination risk.
- Do compress candidate representation to the minimally discriminative fields (short title, 3-5 key attributes, price, category, rating) and use compact delimited/numbered-list formatting for prompt *input*, reserving strict JSON/schema validation for the *output* side.
- Do fuse signals (retrieval score, reranker rank, LLM rank, price-fit, rating) via a training-free method like RRF, or a hand-tuned weighted blend validated against the eval set — this is explicitly permitted "local scoring-logic tuning."
- Do cache reranking results keyed on normalized dialogue state/slots rather than raw utterance text, to avoid recomputing identical rerank work across turns.
- Do add a confidence-based early exit / skip-LLM-rerank path when cheaper-stage score margins are already decisive, to protect the turn-latency budget.
- Do explicitly test and mitigate LLM listwise position bias (shuffle candidate order across repeated calls, or use an explicit debiasing instruction) if a listwise LLM stage is used.
- Do treat a strong, dependency-free cross-encoder baseline as a first-class deliverable, not just a fallback — several 2025-2026 benchmarks found it can match or beat general-purpose LLM rerankers outright.

## Don'ts

- Don't rerank the full retrieval pool (tens of thousands of catalog items or even hundreds of retrieved candidates) with an LLM call — every source confirms this is the dominant latency/cost driver and is unnecessary given retrieval already narrows the pool.
- Don't use pointwise LLM scoring at scale (one call per candidate) as the primary ranking mechanism — benchmarked as the worst latency/cost/accuracy combination among LLM paradigms.
- Don't rely on RankGPT's sliding-window mechanism for our use case — it exists to rank 100+ candidates within context limits, which is a different problem than ours (we should just shrink N instead of adding windowing latency).
- Don't assume an off-the-shelf web-search-trained cross-encoder (MS MARCO-tuned) transfers perfectly to the Amazon Clothing/Shoes/Jewelry domain without any local calibration — validate on a held-out slice and be ready to blend in domain heuristics (title/category token overlap, brand match) if it underperforms.
- Don't build the pipeline so the "LLM Semantic Ranking" requirement can only be satisfied when a paid API key is present — this single point of failure directly threatens the evaluation, given the organizer explicitly does not guarantee API access.
- Don't feed the LLM the full accumulated dialogue transcript every turn if it can be reduced to structured slots/intent — this needlessly grows prompt size and latency turn-over-turn within the 10-turn budget.
- Don't use unconstrained pairwise tournament reranking (O(K²) comparisons) under a hard per-turn latency ceiling — it is the most expensive paradigm surveyed and scales worst with candidate count.
- Don't conflate "in-memory only, no external vector DB clusters" with "no reranking model at all" — a local cross-encoder or late-interaction scorer running in-process is fully compliant and is the recommended default, not a workaround.
