# Dialogue State Tracking & Slot Management for a Turn-Constrained Shopping Copilot

## Overview

Dialogue State Tracking (DST) is the component of a task-oriented dialogue (ToD) system that maintains a structured summary — the "belief state" — of what the user wants, updated turn by turn from the raw conversation. Classically (MultiWOZ, DSTC, SGD-era systems, ~2018–2021) this was framed as a supervised classification/generation problem over a fixed domain-slot ontology, trained on tens of thousands of annotated dialogues, and scored with Joint Goal Accuracy (JGA) — the belief state must match the gold state *exactly* every turn.

Since 2023, the field has largely shifted toward **LLM-based, zero-/few-shot DST**: instead of training a tracker, an LLM is prompted (or given a function/JSON schema) to read the dialogue so far and output the updated state directly, or to output an *update operation* (add/keep/overwrite/delete) per slot. This shift matters a lot for our project, because it removes the "no FM training" constraint's biggest obstacle — classical DST assumed you'd train a tagger; LLM-based DST assumes you already have a capable model and only need a well-designed prompt/schema and light control logic around it.

Our system's specific difficulty is not standard slot-filling (which is nearly solved by prompting) but the **accumulation-vs-override decision**: given a new user utterance and an existing belief state, decide whether the new information should be merged into the state (refinement) or should replace/clear parts of it (topic/intent change). This is exactly the problem addressed by SOM-DST's per-slot operation classification, MultiWOZ's "dontcare"/"none" special values, and, more recently, papers explicitly about LLM "context switching" and "topic shift detection" in multi-turn dialogue.

## Key approaches found

### 1. Classical task-oriented DST (MultiWOZ-style belief tracking)

- **MultiWOZ 2.0–2.4** is the standard multi-domain ToD benchmark (restaurant/hotel/train/taxi/attraction), scored by Joint Goal Accuracy; state-of-the-art trained models reach ~55–60% JGA on MultiWOZ 2.1–2.4, degrading on long dialogues due to noisy/irrelevant context ([Dialogue State Tracking with Sparse Local Slot Attention, ACL 2023](https://aclanthology.org/2023.nlp4convai-1.4/); [Emergent Mind DST overview](https://www.emergentmind.com/topics/dialogue-state-tracking-dst)).
- **SOM-DST (Selectively Overwriting Memory, ACL 2020)** is the most directly relevant classical architecture: it treats the belief state as a fixed-size memory (slot → value) and, each turn, runs a **state operation predictor** that assigns one of four operations to *every* slot: `CARRYOVER` (keep as-is), `DELETE` (clear), `DONTCARE` (mark irrelevant), `UPDATE` (regenerate value from a slot-value generator). Only slots tagged `UPDATE` get new values generated, which is both more accurate and far more efficient than regenerating the whole state every turn. ([arXiv:1911.03906](https://arxiv.org/abs/1911.03906); [GitHub: clovaai/som-dst](https://github.com/clovaai/som-dst)). This ADD/KEEP/DELETE/UPDATE operation taxonomy is a clean, reusable **conceptual pattern** even without SOM-DST's trained neural components.
- **Slot carryover** literature (Google SGD-era) distinguishes *in-service carryover* (reusing a value mentioned earlier in the same domain) from *cross-service carryover* (reusing a value like a city name across different domains/services) — relevant to our category-switch scenario (dress → shoes) where some slots like "size" or "budget" might legitimately carry over across categories while others (color, style) should not.
- **Verdict**: the trained neural machinery (BERT/GPT-2 encoders, slot-value generators trained on thousands of labeled turns) is overkill and disallowed by "no FM training." What's reusable is the *design pattern*: (a) fixed slot schema, (b) per-slot operation label each turn, (c) explicit "dontcare"/"none" values instead of silently deleting information.

### 2. LLM-based / prompt-based state tracking

- LLMs (GPT-3.5/4, LLaMA with instruction tuning) can perform zero-/few-shot DST competitively with fully-trained models when given the schema and good in-context examples; providing examples that show *all* slots of a domain in a single-turn update, rather than abstract task descriptions, improves accuracy ([Emergent Mind](https://www.emergentmind.com/topics/dialogue-state-tracking-dst)).
- **FnCTOD (Function-Calling for Task-Oriented Dialogue, ACL 2024)**: treats each domain's schema as a callable "function"; DST becomes "calling" that function with extracted arguments. This lets the LLM emit structured JSON arguments constrained by a function/tool schema (directly analogous to OpenAI/Anthropic tool-calling or JSON-schema-constrained decoding). With in-context prompting, 7B–13B open models using this scheme surpassed prior ChatGPT-based SOTA, and it improved ChatGPT's own JGA by 5.6 points over baseline prompting ([arXiv:2402.10466](https://arxiv.org/abs/2402.10466), [GitHub: facebookresearch/FnCTOD](https://github.com/facebookresearch/FnCTOD)). **This is the most directly applicable technique for our system**: define the slot schema as a tool/function signature, force the model to emit only valid JSON matching it, and use tool-calling/structured-output APIs (not free-text parsing) to eliminate a large class of formatting errors.
- **ParsingDST (EMNLP 2023 Findings)**: reframes zero-shot DST as text-to-JSON semantic parsing, explicitly designing "intricate updating strategies" (beyond flat slot-filling) so the JSON produced each turn correctly reflects *update operations*, not just final values; shows JGA/slot-accuracy gains over plain zero-shot prompting on MultiWOZ ([arXiv:2310.10520](https://arxiv.org/abs/2310.10520)). This supports the design choice of having the LLM emit an explicit **diff/operation** (e.g., `{"op": "set", "slot": "color", "value": "red"}` or `{"op": "clear_all"}`) rather than a full replacement state each turn, which is both more robust to hallucination and cheaper to validate.
- **Reliability considerations** repeatedly called out across this literature:
  - Constrain output format via JSON-schema/function-calling rather than free text — free-text slot values regenerated from scratch each turn are prone to drift and formatting inconsistency.
  - Few-shot examples that demonstrate typical *interaction scenarios* (not just isolated slot definitions) measurably improve in-context accuracy.
  - LLM accuracy degrades as dialogue history grows long/noisy — for a 10-turn cap this is a non-issue (context is always short), which works in our favor.
  - Open-weight/smaller models can exhibit "stickiness": they classify a topic shift correctly but still leak old context into the next turn's state (see item 3) — so detection and application of the operation should be enforced by code, not left to a single LLM call to both decide and apply silently.

### 3. Detecting intent override vs incremental refinement

This is the crux of our "Dynamic State Machine" requirement, and it maps onto an active sub-area: dialogue **topic-shift / context-switch detection**.

- **"Beyond Continuity: Challenges of Context Switching in Multi-Turn Dialogue with LLMs" (2026)** frames the problem exactly as we need it: a binary per-turn classification of **PIVOT** (topic/intent switch — old context should be discarded) vs **REFINE** (continuation — old context should be kept/merged). Key findings: (a) models often *correctly say* a pivot occurred while *still leaking* old slot values into the new state ("stickiness") — meaning classification and state-mutation must be enforced as separate, auditable steps, not trusted to happen atomically inside one LLM response; (b) **position bias** — pivot detection gets worse the later in the conversation it happens, because models over-weight accumulated coherent context; (c) mitigations include a **two-stage controller** that separates "did the topic change?" from "what do we do with the state?", explicit **anti-anchoring prompts**, and **position-aware priors** that raise the prior probability of a pivot as the conversation gets longer. ([arXiv:2605.09268](https://arxiv.org/html/2605.09268v1))
- **"Multi-Granularity Prompts for Topic Shift Detection in Dialogue" (2023)** proposes extracting topic signal at three granularities — label (topic category), turn (single utterance), and topic (running thread) — and shows this multi-level view beats single-encoding baselines on Chinese/English topic-shift datasets (CNTD, TIAGE). Useful takeaway even without adopting the model: **check for a shift signal at more than one granularity** (category-level: does the new utterance name a different top-level category/facet set than current slots?; lexical-level: explicit phrases like "actually", "never mind", "instead", "forget that"; semantic-level: low similarity between the new utterance and the utterances that produced the current slots). ([arXiv:2305.14006](https://arxiv.org/pdf/2305.14006))
- **Contradiction/conflict detection as a proxy for override**: literature on dialogue contradiction (ParlAI's "Addressing Contradictions in Dialogue Modelling", [arXiv:2012.13391](https://arxiv.org/pdf/2012.13391)) and DST conflict handling describes detecting a conflict when a slot value is overwritten *and* the new utterance is semantically distant from the utterance that set the old value — e.g., belief state has `hotel-area=north`, user says "actually, I'd prefer the south side" → conflict flagged, slot updated. This generalizes directly to our category case: if the new utterance's product-category/attribute vocabulary has near-zero overlap with the vocabulary that filled the *current* category slot, that is itself the override signal — no separate contradiction-classifier is needed if the category taxonomy is small and known in advance (as it is for a frozen catalog).
- **Explicit negation/reset cues** ("never mind", "actually", "instead", "no, I want...", "forget the dress") are simple, cheap, high-precision triggers that most production systems (Rasa forms, etc.) use as a first-pass rule layer before falling back to semantic/LLM judgment. Rasa's own docs describe a "soft reset" pattern: an intent/action can explicitly clear specific slots or deactivate a form and reset "requested" slots rather than merging blindly ([Rasa forms docs](https://legacy-docs-oss.rasa.com/docs/rasa/forms/); [Rasa slots reference](https://rasa.com/docs/reference/primitives/slots/); [GitHub RasaHQ/rasa#3949 "soft reset while maintaining slot values"](https://github.com/RasaHQ/rasa/issues/3949)).
- **Category-level conflict as the strongest, cheapest signal for our domain**: because the catalog is a single product vertical (`Clothing_Shoes_and_Jewelry`) with a bounded, known category taxonomy (dresses, shoes, jewelry, tops, etc.), a rule "if the newly-extracted top-level category differs from the currently-held top-level category, treat this as an override and clear category-dependent slots (color, size, style, fit) while optionally preserving category-independent ones (budget, brand, gift-recipient)" is both simple to implement and matches exactly what the "Beyond Continuity" and SOM-DST literature converge on as the dominant real-world override case. This should be a **deterministic rule**, not an LLM judgment call, since it is unambiguous and free of the "stickiness"/leakage failure mode.

### 4. Slot decay over time

"Slot decay" appears in the conversational-search/CRS literature in a few related senses, none of which requires trained models:

- **Confidence/recency decay**: older slot values that were inferred with lower confidence, or that have not been re-confirmed by subsequent turns, have their "weight" reduced over time so that newer, more specific information dominates ranking/filtering even if the old slot was never explicitly cleared. This is analogous to exponential decay of relevance weights in long-running conversational memory systems, e.g., decay factors applied so that stale entries lose influence as a session progresses ([LANTERN: Layered Archival and Temporal Episodic Retrieval Network, arXiv:2606.05182](https://arxiv.org/pdf/2606.05182) discusses confidence-decay in long-context conversation stores, concentrated where the store prunes stale entries).
- **Positional decay in slot elicitation**: in some CRS formulations a slot-dependent decay factor λᵢ ≤ 1 lowers the expected answer/engagement rate the later a slot is asked about in a session, motivating systems to front-load the most discriminative slots ([CRS survey discussion, arXiv:2004.00646](https://arxiv.org/pdf/2004.00646)).
- **Practical implementation pattern for a 10-turn, in-memory system**: rather than a continuous decay function (which needs tuning and adds nondeterminism), the typical lightweight implementation is a **soft/hard confidence tier** per slot: `confirmed` (explicitly stated this turn or very recently and never contradicted), `inferred` (derived indirectly, e.g. from a clicked product, or stated many turns ago) , and `stale/expired` (superseded by a category change, or old enough — e.g., more than N turns without reinforcement — that it should stop constraining retrieval and instead just bias re-ranking). Given our 10-turn ceiling, a simple **turn-count TTL** (e.g., an unconfirmed slot loses filtering power after ~3–4 turns of not being mentioned again, but a *confirmed* slot never expires within the session) is sufficient and avoids over-engineering; full continuous decay curves are unnecessary complexity for sessions this short.
- Decay is primarily a **ranking/soft-constraint** mechanism, not a hard-delete mechanism — it should demote a slot's influence on filtering/scoring, while explicit override/clear (section 3) remains the mechanism for removing a slot outright. Conflating the two (using decay logic to also decide category resets) reintroduces the ambiguity that rule-based category conflict detection is meant to avoid.

### 5. Correctness and speed within a 10-turn hard budget

- Because MTTC (mean turns to conversion) is scored and a 10-turn overrun is a hard zero, the state tracker must **never spend a turn purely re-confirming state it can already trust**. This argues against classic ToD patterns like explicit confirmation sub-dialogues ("So you want a red dress under $50, is that correct?") that are common in voice/telephony ToD systems (where ASR errors justify confirmation) — text input here is pre-cleaned, so confirmation turns are pure waste.
- The dominant cost driver in LLM-DST accuracy studies is **long, noisy history** — with a 10-turn cap this risk is inherently small, so a design can afford to pass the *entire* turn history (not a compressed summary) to the state-tracking step each turn without hitting the degradation regime reported in longer MultiWOZ dialogues (20+ turns). This means the extraction step can prioritize simplicity (full-context prompt) over engineering effort spent on context compression.
- Latency/robustness argue for making the tracker a **single structured-output LLM call per turn** (extract-and-diff in one shot, schema-constrained) plus **deterministic post-processing rules** (category-conflict clear, negation-cue override, TTL decay) rather than a multi-call pipeline (e.g., separate calls for "detect shift" then "extract slots" then "apply diff") — every extra LLM call adds latency and another point of failure, which is costly when only 10 turns are available to reach a hit.
- Given the single-user, single-session, in-memory nature of the task, there is **no need for the DST module to persist state externally or handle concurrent belief-state merges** — the entire "Dynamic State Machine" can be a plain in-memory object (e.g., a dict) mutated in place each turn; this is a simplification classical DST work doesn't get to assume (SGD/MultiWOZ systems must handle service handoffs and cross-session persistence).
- Turn efficiency literature on ToD systems explicitly measures "average number of turns to task completion" as a system-quality metric and recommends **proactive/mixed-initiative** dialogue management (system asks for the most discriminative missing slot rather than a fixed slot order) to cut turns — directly supporting front-loading category/budget before finer attributes like exact size/fit if the policy layer (outside DST scope here) needs to choose what to ask next ([Survey on Recent Advances in LLM-Based Multi-turn Dialogue Systems, arXiv:2402.18013](https://arxiv.org/html/2402.18013v1)).

### 6. Conversational Recommender System (CRS) prior art and lightweight implementations

- **"A Survey on Conversational Recommender Systems" (Jannach et al., 2020/ACM CSUR)** frames most CRS as explicitly maintaining slot-value pairs representing accumulated user preferences (e.g., `[food=Japanese, location=95070]`) fed into a policy network that decides whether to ask another question or recommend; it explicitly separates *belief tracking* (our concern) from *policy* (what to ask/recommend next) — a separation worth preserving in our architecture so the state tracker stays simple and reusable regardless of how the retrieval/ranking policy evolves ([arXiv:2004.00646](https://arxiv.org/pdf/2004.00646)).
- **"Conversational recommendation: A grand AI challenge" (Jannach, AI Magazine 2022)** and the CRS evaluation survey ([Jannach et al., AI Review 2022](https://link.springer.com/article/10.1007/s10462-022-10229-x)) both note that most deployed/lightweight CRS still use simple slot-filling with hand-authored dialogue policies rather than end-to-end neural belief trackers, because the neural approaches need large annotated interaction logs that most commercial systems don't have — reinforcing that a lightweight rule+LLM hybrid is not just permissible under our constraints but is the *mainstream pragmatic choice* even outside hackathon constraints.
- **Rasa forms/slots** (a widely used open-source ToD framework) is the best-documented example of a lightweight, non-neural, rule-based slot manager: slots are filled via configurable "slot mappings," validated with custom validation actions, and can be explicitly cleared or a form "soft-reset" without discarding the whole conversation — a good structural template (schema + mapping + explicit reset action) even though we will use an LLM instead of Rasa's NLU pipeline for extraction ([Rasa forms](https://legacy-docs-oss.rasa.com/docs/rasa/forms/), [Rasa slots reference](https://rasa.com/docs/reference/primitives/slots/)).
- No widely-known, maintained open-source repo was found that is specifically "a lightweight rule+LLM hybrid state tracker for a shopping bot" as a named, reusable library; several e-commerce chatbot repos surfaced (RetailGPT, tomlin7/ecommerce-chatbot, OpenAI-function-calling cart bots) use LLM function-calling to extract structured order/cart data from free text, which is the same mechanism (schema-constrained extraction) recommended here for slot extraction, just applied to carts instead of search facets ([unicamp-dl/retailGPT](https://github.com/unicamp-dl/retailGPT), [tomlin7/ecommerce-chatbot](https://github.com/tomlin7/ecommerce-chatbot)). Treat these as validation that structured-output LLM extraction is standard practice in shopping-bot contexts, not as a state-tracking reference implementation to copy wholesale.

## Relevance to our constraints

| Constraint | Implication for DST design |
|---|---|
| 10-turn hard cap, zero score if exceeded | No confirmation turns; no multi-call detect-then-extract pipelines that risk latency/failure; front-load discriminative slots; decay/TTL windows must be small (2-4 turns, not dozens) |
| No FM training | Rules out SOM-DST-style trained operation predictors and any fine-tuned DST model; favors zero-/few-shot LLM prompting (FnCTOD/ParsingDST-style) plus deterministic rule layers |
| Catalog read-only, in-memory only | State tracker is a plain in-memory struct/dict; no persistence, no cross-session merge logic needed |
| Text-only, pre-cleaned input | No ASR-confidence-driven confirmation needed; negation/reset cue detection can be simple string/keyword or embedding-similarity checks rather than robust-to-noise NLU |
| Single isolated user per session | No concurrency, no multi-user slot namespace collisions; simplifies the "state" to one flat object |
| Evaluated on Hit Rate@K, MRR, MTTC | State correctness matters more than exhaustive slot coverage; wasted/incorrect turns (over-merging after a topic change, or over-clearing during refinement) directly hurt MTTC and thus should be the top design priority over marginal JGA-style precision |

## Recommended approach(es) with rationale

**Recommended architecture: schema-constrained LLM extraction + deterministic operation rules, in that order, each turn.**

1. **Fixed slot schema per category** (e.g., category, sub-category, color, size, price_min/max, brand, material, occasion/style, gift-recipient) defined as a JSON schema / tool signature, following the FnCTOD/function-calling pattern. Each turn, call the LLM once with (a) the full turn history — short enough at ≤10 turns that context degradation is not a concern — and (b) the current belief state, and ask it to return a **diff/operation list**, not a full replacement state: entries like `{"slot": "color", "op": "set", "value": "red"}`, `{"slot": "*", "op": "clear_category"}`, `{"slot": "size", "op": "keep"}`. Modeling output as explicit per-slot operations (ADD/KEEP/UPDATE/CLEAR — the SOM-DST taxonomy, produced via LLM instead of a trained classifier per ParsingDST/FnCTOD) makes the update auditable and cheap to validate against the schema, and sidesteps the "stickiness" failure mode where a single free-form JSON-state output silently drops or leaks slots.

2. **Deterministic pre/post rules layered around the LLM call, not delegated to it**, because the literature consistently shows LLMs can *say* the right classification while still leaking old state:
   - **Category-conflict rule (primary override trigger)**: if the LLM (or a cheap keyword/embedding check against the known category taxonomy) detects that the new utterance's top-level category differs from the currently held category, force-clear all category-dependent slots (color, size, style, fit, material) regardless of what the LLM's diff says, and keep only category-independent slots (budget ceiling, brand if generic, gift-recipient) unless the user's utterance also contradicts those. This single rule covers the dress→shoes example in the prompt and is the highest-precision, lowest-cost signal available given a small known category taxonomy.
   - **Explicit reset-cue rule**: a short keyword/phrase list ("never mind", "actually", "instead", "forget that", "no I want", "not X, Y") that, when matched, biases toward CLEAR/OVERWRITE even without a category change (covers within-category pivots, e.g., "red dress" → "actually, blue").
   - **Everything else defaults to ADD/merge** (information accumulation) — the common case, and the one that must never be mistakenly treated as an override, since over-clearing wastes turns and directly hurts MTTC.
   - Apply the LLM's returned operations only after these two cheap deterministic checks either confirm or override them — the deterministic layer is the safety net, the LLM does the semantic heavy lifting (extracting values, handling paraphrase/synonymy the rules can't enumerate).

3. **Slot confidence/decay as a soft ranking signal, separate from clear/override logic**: tag each slot `confirmed` vs `inferred`, and apply a short turn-count TTL (e.g., an inferred, unconfirmed slot stops constraining hard filters after ~3 turns of not being reinforced, but a confirmed slot never expires mid-session). Use decay to demote ranking weight, not to trigger clears — clears are owned exclusively by the category-conflict/reset-cue rules above, keeping the two mechanisms orthogonal and each individually simple to reason about and test.

4. **No confirmation turns, no multi-stage LLM pipeline.** One schema-constrained extraction call per turn is enough; do not add a separate "did the topic shift?" LLM call before extraction — fold that decision into the same call's output plus the deterministic category-rule override, to keep latency and turn budget low.

This combination is cheap (one LLM call/turn + O(1) rule checks), needs no training data, matches how FnCTOD/ParsingDST structure LLM-based DST output, and directly targets the two literature-documented failure modes (stickiness/leakage on pivots, and over-eager clearing on refinements) with a rule layer precisely where LLM judgment is least reliable (category-level, unambiguous conflicts) and LLM judgment precisely where rules can't scale (open-ended attribute extraction and paraphrase handling).

## Dos

- **Do** define a small, fixed, explicit slot schema (per top-level category, if categories have different attribute sets) and use JSON-schema/function-calling-constrained LLM output to fill it — do not rely on free-text parsing.
- **Do** have the model emit an explicit **operation per slot or per group of slots** (add/keep/update/clear) rather than only a bare replacement state, so overrides are auditable and testable independent of extraction quality.
- **Do** treat a **category/domain change as the dominant, highest-precision override signal** and handle it with a deterministic rule (not an LLM judgment call), since the catalog's category taxonomy is small, known, and fixed.
- **Do** use simple negation/reset lexical cues ("actually", "never mind", "instead") as a cheap secondary override trigger, mirroring how production frameworks (Rasa) implement soft resets.
- **Do** keep decay/TTL logic separate from override/clear logic: decay softly demotes stale, unconfirmed slots in ranking; override/clear hard-removes slots on detected topic/category change.
- **Do** pass full turn history to the extraction step each turn — at ≤10 turns you are well within the regime where LLMs handle context reliably, so there's no need to build history compression.
- **Do** keep the state as a single plain in-memory object; there is no multi-session or multi-user concern to design around.
- **Do** prioritize preventing wasted/incorrect turns (wrong merge or wrong clear) over maximizing slot-extraction recall, since MTTC directly penalizes turns spent recovering from a bad state update.

## Don'ts

- **Don't** implement or adapt a trained neural DST model (SOM-DST, TRADE, graph-enhanced GPT-2 trackers, etc.) — they need labeled training data and violate the no-FM-training constraint; use their *design patterns* (operation taxonomy), not their weights or training pipelines.
- **Don't** trust a single LLM call to both *decide* there was a topic shift and *silently* apply the consequence in the same breath without a deterministic check — literature shows models can verbally acknowledge a pivot while still leaking old slot values into the merged state.
- **Don't** add explicit confirmation turns ("Just to confirm, you want...") to compensate for extraction uncertainty — with clean text input and a 10-turn cap, these turns are pure waste and directly harm MTTC.
- **Don't** build a continuous/tunable decay function (exponential half-life, learned decay weights, etc.) — sessions are too short (≤10 turns) for such a mechanism to matter; a simple confirmed/inferred tag plus a small turn-count TTL is sufficient and far easier to verify.
- **Don't** conflate slot decay (soft ranking demotion) with slot clearing (hard removal on override) — they solve different problems and merging their logic reintroduces the exact ambiguity the override-detection rules are meant to eliminate.
- **Don't** run a multi-stage pipeline (separate shift-detection call, separate extraction call, separate diff-application call) purely for architectural cleanliness — each added LLM call is added latency and another failure point that a 10-turn budget can't absorb.
- **Don't** assume position-independent reliability — several papers note pivot-detection accuracy degrades later in a conversation; if anything, bias the deterministic category-rule to be *more* trusted (not less) as the session progresses, rather than relying more heavily on the LLM's own judgment.
