# Adaptive / Dynamic Runtime Orchestration for the Shopping Copilot

Research brief translating TikTok TechJam Track 4's "Adaptive Orchestration: dynamic Context Programming to achieve runtime workflow re-orchestration and strategy alignment" requirement into established, implementable techniques, scoped to a 72-hour hackathon build with a frozen catalog, ≤10 turns/session, in-memory, text-only, no FM training.

## Overview

The rubric phrase is marketing language for a real and well-studied idea: **an agent pipeline that changes its own control flow at runtime based on the state it has accumulated so far**, instead of always executing the same fixed sequence of steps. This is not a single named technique — it's a design goal that established agentic-systems literature approaches from several angles:

- **Control-flow adaptivity**: which steps run at all, and in what order (routing, plan/replan, skip-stage optimizations).
- **Context adaptivity** ("context engineering"): what information is assembled and re-injected into the LLM's context at each step, compressed/curated rather than a static mega-prompt.
- **Strategy adaptivity**: which weighting/parameters/thresholds a given step uses (e.g., retrieval blend weights, clarification aggressiveness), chosen based on signals like confidence, turn budget, and result-set characteristics.

All three map cleanly onto "runtime re-orchestration and strategy alignment ensuring the agent iteratively refines its own guidance logic" — the "guidance logic" is the routing/weighting policy, and "iteratively refines" means it is recomputed turn-by-turn from fresh state, not hardcoded once. Crucially, **none of this requires training a model or an RL loop**; it can be built as a rule-based or lightly-LLM-assisted controller sitting above a mostly-fixed set of retrieval/generation primitives.

## Translating "Dynamic Context Programming" into concrete, implementable mechanisms

| Rubric phrase | Concrete technical concept | What it looks like in code |
|---|---|---|
| "Dynamic Context Programming" | Context engineering / context assembly per turn | At each turn, decide what goes into the LLM prompt: which slots are filled, which candidate products, which prior turns are summarized vs. dropped. Not a static system prompt — a function of current dialogue state. |
| "Runtime workflow re-orchestration" | Conditional routing between sub-pipelines / stage-skipping | A controller (state machine or lightweight policy) decides, per turn: run retrieval only vs. retrieval+rerank; ask a clarifying question vs. show results; widen vs. narrow filters. |
| "Strategy alignment" | Parameter/weight selection conditioned on signals | Hybrid retrieval blend (dense vs. sparse/filter weight) is not a fixed constant — it's chosen per turn from candidate-pool size, query specificity, slot-fill confidence. |
| "Iteratively refines its own guidance logic" | Feedback-conditioned re-planning across turns (Reflexion-style, not weight updates) | After each turn's outcome (result count, user's next utterance), the controller updates its *beliefs* (slot confidence, remaining turn budget) and that changes next turn's strategy — refinement of the policy's *inputs*, not the policy's *code*. |

The key translation for judges/writeup: **this is "context engineering" (Anthropic's 2025 term) plus classic "workflow" patterns (Anthropic's routing / orchestrator-workers / evaluator-optimizer), not a novel technique** — and that's a feature, not a weakness, for a 72-hour build: it means there's a large, well-tested design vocabulary to borrow from rather than inventing something bespoke and unverifiable.

## Key approaches found (with inline citations/links)

**Reasoning+acting loops**
- **ReAct** (Yao et al., 2022, ICLR 2023) interleaves reasoning traces with actions so the model can "induce, track, and update action plans" and "handle exceptions" mid-episode — the earliest clean example of an LLM changing its own next step based on an intermediate observation rather than following a pre-set script. [arXiv:2210.03629](https://arxiv.org/abs/2210.03629), [project page](https://react-lm.github.io/)

**Self-critique / strategy revision across turns**
- **Reflexion** (Shinn et al., 2023) converts environment feedback into a verbal self-reflection stored in an episodic memory buffer and re-injected into the next attempt, functioning as a "semantic gradient" without any weight updates. Directly analogous to "iteratively refines its own guidance logic" purely via context, not training. [arXiv:2303.11366](https://arxiv.org/abs/2303.11366)

**Plan-and-execute with replanning**
- LangChain's **plan-and-execute** architecture separates a planner (multi-step plan LLM call) from executors, with an optional **re-planner node** that inspects the current state after each step and decides: continue plan, generate a new plan, or terminate — "error-driven replanning" for dynamic adaptation. This is close to a lightweight version of runtime re-orchestration for a shopping agent (e.g., replanning retrieval after a clarification answer). [LangChain blog](https://www.langchain.com/blog/planning-agents)
- Related: **Plan-Execute-Verify-Replan** frameworks add an explicit verify step before deciding whether to replan, which maps to "check retrieval confidence before deciding whether to rerank or re-ask." [arXiv:2603.11445](https://arxiv.org/html/2603.11445v2)

**Anthropic's "workflows" taxonomy** (the closest vendor-endorsed vocabulary for this rubric item)
- Anthropic's "Building Effective Agents" distinguishes **workflows** (LLMs/tools orchestrated through *predefined* code paths — routing, parallelization, orchestrator-workers, evaluator-optimizer) from fully autonomous **agents**. The **routing** pattern (classify input, dispatch to a specialized handler) and **evaluator-optimizer** pattern (one call generates, another critiques/decides to retry) are exactly the granularity of "adaptive orchestration" a hackathon system should aim for — conditional branches within an otherwise fixed pipeline, not free-form autonomy. [Anthropic engineering blog](https://www.anthropic.com/engineering/building-effective-agents) (see also secondary summaries: [Baeldung](https://www.baeldung.com/spring-ai-building-effective-agents), [Spring AI reference](https://docs.spring.io/spring-ai/reference/api/effective-agents.html))

**Context engineering (2024-2025 term)**
- Anthropic (2025) defines context engineering as "the set of strategies for curating and maintaining the optimal set of tokens during LLM inference," covering context editing (rule-based pruning), context awareness (surfacing remaining budget to the model), and keeping context "informative yet tight" rather than static. [Anthropic: Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- LangChain's parallel treatment frames context engineering as "building dynamic systems to provide the right information and tools in the right format such that the LLM can plausibly accomplish the task" — explicitly a systems/plumbing problem, not a prompting trick. [LangChain: Context Engineering for Agents](https://www.langchain.com/blog/context-engineering-for-agents)
- Related risk research: "context rot" — LLM recall degrades as context grows, motivating *compression* over *accumulation* as turns progress. [Anthropic engineering blog, context rot discussion]

**Adaptive retrieval (the closest real analog — retrieval-pipeline adaptivity)**
- **Adaptive-RAG** (Jeong et al., NAACL 2024) routes queries through no-retrieval / single-step / multi-step retrieval strategies based on a predicted query-complexity label, trained on a small classifier over automatically-derived complexity annotations — directly the "skip a stage when confidence is already high" pattern, generalized from QA to (in our case) a shopping query. [arXiv:2403.14403](https://arxiv.org/abs/2403.14403), [ACL Anthology](https://aclanthology.org/2024.naacl-long.389/), [reference implementation](https://github.com/AsH1605/Adaptive-RAG)
- **Self-RAG** (Asai et al., 2023) trains a model to emit "reflection tokens" that decide *on-demand* whether retrieval is needed at all and whether generated output is well-supported/relevant — the adaptivity is baked into token generation rather than an external controller. Requires fine-tuning, so it's a conceptual reference for us, not something to reproduce (no FM training allowed). [arXiv:2310.11511](https://arxiv.org/abs/2310.11511), [project site](https://selfrag.github.io/), [code](https://github.com/akariasai/self-rag)
- **RAGRouter-Bench** / lightweight query routing work (2025-2026) shows that a small, even rule-based, three-class complexity router can match "always do the expensive thing" baselines at a fraction of the cost — i.e., you don't need a trained model to get most of the benefit of adaptive routing. [arXiv:2604.03455](https://arxiv.org/pdf/2604.03455)
- **DAT — Dynamic Alpha Tuning** (2025) dynamically sets the dense/BM25 blend weight α per query by having an LLM score the top-1 result from each retriever and normalizing those scores into a weight, rather than using a fixed α for the whole collection. Directly the "filter-track vs. dense-track weighting per turn" idea named in the task — though DAT's specific method costs an extra LLM call per query, which is a latency/turn-budget tradeoff to weigh against a cheaper heuristic version (e.g., weighting by candidate-pool size or query token overlap with catalog vocabulary instead of an LLM judgment). [arXiv:2503.23013](https://arxiv.org/abs/2503.23013)
- Broader 2025 framing: "the 2025 frontier is per-query dynamic alpha — detecting whether an incoming query is keyword-heavy or semantic, and adjusting α accordingly at query time rather than per-collection," confirming this is an active, well-understood retrieval-engineering pattern rather than a speculative idea. (See also production discussion: [BM25 still wins on the queries that matter](https://tianpan.co/blog/2026-04-12-hybrid-search-production-bm25-dense-embeddings))

**Confidence-gated routing / stage-skipping**
- General LLM-routing literature describes confidence gates mapping a score to discrete actions (serve directly / verify / escalate) — the same mechanical pattern as "skip LLM reranking when retrieval confidence is already high." [Confidence-Based Routing in LLM Systems](https://medium.com/@udayansawant/confidence-based-routing-in-llm-systems-629aa5564567)

**Conversational recommendation / clarification-turn policy**
- Conversational recommender system (CRS) literature frames the exact per-turn decision our agent faces: *ask a clarifying question vs. commit to a recommendation now*, with systems like UNICORN using RL to unify "what to ask / what to recommend / when to ask or recommend" into one policy, and explicitly noting the system should "succeed using the least number of turns, as users lose patience after too many turns." This validates turn-budget-aware escalation/de-escalation of clarification aggressiveness as a known, named problem (not something we're inventing), even though the canonical solutions use RL/training which is off the table here — the direction of the effect (fewer turns left → be more decisive, ask higher-value questions or none) can be encoded as a hand-written rule instead. [Survey: Advances and challenges in CRS](https://www.sciencedirect.com/science/article/pii/S2666651021000164), [Learning to Ask Appropriate Questions in CRS](https://arxiv.org/abs/2105.04774)

**State-machine vs. LLM-as-orchestrator control**
- Comparative framing across ~70 surveyed agent systems: state-machine control gives "medium expressiveness but high controllability," and sits closer to the "predictable workflow" end of a predictability-adaptability frontier, vs. free-form LLM orchestration which sits at the adaptive-but-unpredictable end. A recommended pragmatic middle path for dialogue systems: **an explicit FSM-style spec (typed slots, validators, small explicit transitions) as the reliable control plane, with the LLM used only as the language layer inside each state** — this is close to the exact recommendation we should make for this project. [Voice agents as state machines](https://medium.com/@manavisrani07/the-secret-to-reliable-voice-agents-treat-prompts-like-state-machines-2323a616affa), [State-driven/graph orchestration overview](https://apxml.com/courses/multi-agent-llm-systems-design-implementation/chapter-4-advanced-orchestration-workflows/state-graph-orchestration), [MetaAgent: multi-agent systems from FSMs](https://arxiv.org/pdf/2507.22606)

**Over-engineering risk (agentic systems generally)**
- Practitioner and applied-research consensus: "complexity is one of the biggest threats to the reliability and maintainability of agentic workflows... avoid unnecessary structural complexity and over-engineering," and pipelines should insert explicit validation/boundary checks between stages rather than trusting free-flowing autonomous handoffs — directly supports keeping the adaptive layer small and auditable. [O'Reilly: The Hidden Cost of Agentic Failure](https://www.oreilly.com/radar/the-hidden-cost-of-agentic-failure/), [Production-Grade Agentic AI Workflows guide](https://arxiv.org/html/2512.08769v1)

## Relevance to our constraints (must stay simple enough to build+tune in a 72-hour window)

Given: ≤10 turns/session, frozen catalog, in-memory, text-only, no FM training, evaluated on Hit Rate@K / MRR / MTTC (time/turns-to-conversion) — the following properties of "adaptive orchestration" matter most:

1. **Turn budget is the scarcest resource and the primary eval metric (MTTC).** Any adaptive mechanism should be justified by its effect on turns-to-conversion or hit rate, not by architectural elegance. This argues for adaptivity that *saves* turns/latency (skip unnecessary clarification, skip reranking when confident) over adaptivity that adds LLM calls to decide things a heuristic could decide for free (e.g., DAT's per-query LLM judging call is expensive relative to a 10-turn budget — prefer a cheap heuristic proxy).
2. **No training means the "guidance logic" must be either rule-based (thresholds/state machine) or LLM-prompted per turn — there is no learned router.** Self-RAG and Adaptive-RAG's classifier both require training data/fine-tuning we cannot do; DAT requires a live LLM judge call. The buildable analogs are: (a) hand-written thresholds on retrieval signals (candidate count, score gap/margin, slot-fill confidence), or (b) asking the orchestrating LLM to output a routing decision as part of its normal turn, which is "free" if it's already making a tool call that turn.
3. **In-memory/read-only catalog means retrieval signals are cheap and deterministic to compute** (result-set size, top-score margin, filter-match count) — these make excellent gating signals for a rule-based controller and are far cheaper than an LLM confidence judgment.
4. **Evaluation and debugging time is scarce in 72 hours.** A controller with more than a handful of named states/branches becomes difficult to test against Hit Rate@K/MRR consistently, because behavior becomes path-dependent and harder to regression-test turn-by-turn. This is the direct hackathon expression of the "predictability-adaptability frontier" — we want to sit close to the predictable end.
5. **The rubric only requires *demonstrating* adaptive orchestration exists and is coherent**, not that it be maximally sophisticated. A small number of clearly-labeled, clearly-justified adaptive branch points, each traceable to a concrete signal, is easier to explain in a demo/writeup and easier to defend under judge questioning than an opaque LLM-decides-everything controller.

## Recommended approach(es) with rationale

**Recommendation: a small explicit state machine (5-8 states) with rule-based, signal-gated transitions, augmented by one place where the LLM is allowed to pick between a short enumerated set of strategies (not free-form) as part of its existing turn output.**

Concretely:

- **Controller = explicit states** such as: `intent-parse → slot-fill/clarify → retrieve → (confidence gate) → [rerank | skip-rerank] → present → (feedback) → refine-or-recommend → end`. Each transition is a plain `if/else` on cheap signals already available in-memory: number of candidates after filtering, score margin between top-1 and top-k, number of unfilled high-value slots, turns remaining.
- **Strategy selection = a rule table, not a trained model or a per-turn LLM judgment**, for the retrieval blend weight (e.g., weight dense retrieval higher when the query is descriptive/attribute-free-text; weight filters/sparse higher when strong categorical/attribute slots are already filled) — same spirit as DAT/query-adaptive hybrid search, but implemented as a heuristic function of slot-fill state rather than an LLM-scored top-1 comparison, to avoid the extra latency/turn cost DAT's method implies.
- **Stage-skipping = confidence-gated, one binary decision**: if top-1/top-k score margin and candidate count both clear a threshold, skip LLM reranking and go straight to presentation (saves an LLM call and turn latency — directly improves MTTC without touching Hit Rate@K materially, since a wide margin already signals a good top-1).
- **Clarification aggressiveness = a single explicit function of turns-remaining and slot confidence**: with turn budget ≤10, tighten the bar for asking a clarifying question as turns are consumed (e.g., allow clarification in turns 1-3 if the top result's confidence is below X, but past turn 6 only clarify if candidate count is effectively unusable, otherwise commit to best-effort recommendations) — directly operationalizes "escalating/de-escalating clarification aggressiveness based on remaining turn budget" from the task brief, and is a straightforward, testable rule rather than a learned dialogue policy (which is what real CRS research uses RL for, unavailable to us).
- **Where the LLM is the deciding agent**: only in one place — deciding *what to ask* or *how to phrase the result summary* — never in deciding *whether to retrieve/rerank/skip*, since those should stay deterministic and cheap to keep the pipeline debuggable and consistent across eval runs.

**Rationale**: This sits deliberately on the "explicit-branches-in-an-otherwise-fixed-pipeline" side of the spectrum (Anthropic's "routing"/"evaluator-optimizer" workflow patterns; the FSM-with-LLM-as-language-layer pattern from voice-agent literature) rather than the "LLM decides the whole control flow every turn" side (full ReAct/plan-and-replan agents, orchestrator-workers). It gives us a legitimate, citable claim to "runtime workflow re-orchestration" and "strategy alignment" (the blend-weight and rerank-skip decisions genuinely change per turn based on accumulated context) while remaining: (a) fast to implement in days not weeks, (b) deterministic enough to regression-test against Hit Rate@K/MRR/MTTC without flaky path-dependent behavior, (c) explainable in under a minute to judges as "we have N named adaptive decision points, each gated by a measurable signal," which is a stronger, more credible demo than an opaque "the LLM figures it out" black box.

## Dos

- Do name and enumerate every adaptive decision point explicitly (aim for 3-5, not 10+) and document the exact signal(s) that gate each one — this is what turns "dynamic Context Programming" from a buzzword into an inspectable, defensible design.
- Do prefer cheap, already-computed signals (candidate-pool size, score margin, slot-fill count, turns-remaining) over spending an extra LLM call purely to decide strategy (cf. DAT's LLM-judged alpha — good idea, wrong cost for a 10-turn budget).
- Do bias every adaptive mechanism toward *saving* turns/latency (skip stages when confident) rather than adding steps, since MTTC and the 10-turn cap are hard constraints.
- Do keep the adaptivity read-only with respect to the catalog and stateless across sessions — signals should come from the current session's accumulated dialogue state only, consistent with the in-memory/no-persistence constraint.
- Do treat clarification-aggressiveness-vs-turn-budget as a simple monotonic rule (fewer turns left -> higher bar to ask another question) rather than a learned/RL policy — this mirrors real CRS research's goal without needing RL.
- Do log the routing decision and its triggering signal at each turn (e.g., "skipped rerank: margin=0.31 > threshold=0.2") — this is what makes the system's adaptivity demonstrable in a demo and debuggable during tuning.
- Do reuse Anthropic's own "workflows vs. agents" vocabulary in the writeup/pitch — it is the most directly citable, judge-legible mapping of the rubric's language to established practice.

## Don'ts

- Don't build a fully autonomous "LLM decides everything every turn" orchestrator (full plan-and-replan or orchestrator-workers style) — with only 10 turns and a hackathon timeline, the added unpredictability costs more in eval-tuning time than it could plausibly gain in Hit Rate@K/MRR.
- Don't try to reproduce Self-RAG or Adaptive-RAG's trained classifiers/reflection tokens — both require fine-tuning or training data pipelines explicitly ruled out by the "no FM training" constraint; use their *design idea* (skip/adjust retrieval based on a complexity/confidence signal), not their *implementation*.
- Don't let the state machine grow past a handful of states "just in case" — each additional state/branch multiplies the paths that need separate eval validation within a fixed 72-hour window.
- Don't put irreversible or expensive decisions (e.g., an LLM call to judge retrieval quality per query, as DAT does) on the hot path of every single turn if a free heuristic proxy achieves comparable gating quality — reserve LLM judgment calls for the turns where they're least substitutable (e.g., final answer phrasing).
- Don't conflate "context engineering" with "bigger prompt" — the term specifically means curating/compressing what's re-injected each turn; don't let dialogue history or full candidate lists accumulate unpruned across up to 10 turns (context-rot risk), even though the catalog is small.
- Don't make the adaptive logic implicit inside a single giant LLM prompt ("use your judgment about whether to ask a question or search") — this is the least controllable and least testable option, and would undercut a judge's ability to verify the "adaptive orchestration" claim at all.
