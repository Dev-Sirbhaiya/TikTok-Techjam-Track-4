# 07 — Risk Register

| # | Risk | Likelihood | Impact | Mitigation | Watch during |
|---|---|---|---|---|---|
| R1 | Any code path allows a session to exceed 10 turns | Low if built correctly | Catastrophic (hard zero for that session) | NFR-1: `turns_remaining <= 1` forces `"commit"` structurally in `turn_policy.py`, not a soft preference | Phase 0.9-0.10, every subsequent change to turn_policy.py |
| R2 | Design assumes a paid LLM API is available; org provides none | Medium (easy to accidentally couple) | High — Phase 0 could fail to run at all in a no-key environment | D-LLM-TIER: cross-encoder is the guaranteed stage; every LLM call wrapped in try/except with a non-LLM fallback | Every module using `llm_client` |
| R3 | Overfitting thresholds/weights to the 200 public dev sessions | High if not disciplined | Medium — private-set TechnicalScore lower than dev-set numbers suggest | `10_PRE_REGISTRATION.md`'s train/validation split; Q8 confirms scenario mix (not products) is shared, so mix-level tuning is safe but product-level overfitting isn't | Phase 1.3 calibration, Phase 3.1 offline tuning |
| R4 | Intent Override sessions (15%) silently scored as failures because a pre-override hit is wrongly counted | Medium (easy to miss this exact mechanic) | Medium — 15% of sessions is a meaningful score chunk | `override_applied` gate explicitly implemented per `wiki/09_simulator_mechanics.md`; Phase 0.5's hand-traced test case | Phase 0.4-0.5, 0.11 integration test |
| R5 | Clarification policy asks too much or too little, tanking Efficiency or HitRate respectively | Medium | Medium-High (both extremes are documented failure modes) | Entropy-gated trigger with calibrated thresholds (0.9), turn-index ceiling, diminishing-returns guard | Phase 0.9, 1.3 |
| R6 | Ambitious Phase 2+ features (multi-interest, bandit) ship without measurable benefit, burning build time the floor needed | Medium-High given time pressure | High — directly threatens Feasibility/Technical Execution scoring | Mandatory ablation gates, `08_ABLATION_MATRIX.md`; Phase 0/1 must be complete and passing before any Phase 2 work starts | Every Phase 2+ item before it's "KEPT" |
| R7 | `details` field's total lack of schema breaks a naive slot-extraction assumption late in the build | Low now (already discovered and designed around) | Low (already mitigated) | Resolved Q7; open-vocabulary internal slots (D10) built from the start | Phase 0.1, 0.4 |
| R8 | Category taxonomy noise (store/brand names appearing as "categories", e.g. "Westlake") corrupts category-based filtering/override detection | Medium | Medium — could cause false-positive override triggers | `retrieval.py`/`overgenerality.py` should validate category tokens against a known-category allowlist derived from frequency/structure, not trust every `categories` entry blindly | Phase 0.1 gazetteer build, 0.5 override rule |
| R9 | Unpublished CPU/memory/timeout limits at final judging cause a working-locally system to fail/timeout at official scoring | Low-Medium (genuinely unknown) | High if it happens (invalid run risk per submission rules) | D-LATENCY: bounded candidate sizes everywhere, no unbounded loops, disclose offline fallback explicitly in README | Phase 5.3 reproducibility check |
| R10 | `codex exec review` becomes unavailable again mid-build (auth expiry) | Low (currently working) | Low (CLAUDE.md already has a graceful-skip + backlog protocol) | Log to `status.md` Blockers immediately if it recurs; commits/wiki-updates continue regardless | Every phase completion |
| R11 | 72-hour clock pressure causes a mid-feature stop that leaves the system in a worse state than the last clean phase | Medium | Medium-High | Per-step commits (not per-phase) mean the last good commit is always recent; `05_BUILD_PLAN.md`'s "if time runs out" section makes stopping cleanly at a phase boundary the explicit default plan | Ongoing |
| R12 | Rocchio-style comparative-feedback update (Phase 3.2) causes query drift, degrading rather than improving results | Medium if built without care | Medium (Phase 3 item only, not floor-threatening) | Bounded/positive-heavy update, k≤5, validation-gated apply (per `research/06` and D9) | Phase 3.2, if attempted |
| R13 | Reported baseline/metrics get mis-attributed (dev vs. private set) in the final writeup | Low | Low-Medium (credibility issue, not a scoring issue) | Q10 resolved explicitly; always label numbers "public dev set" in `wiki/08_evaluation_log.md` and the writeup | Phase 5.1, 5.5 |
