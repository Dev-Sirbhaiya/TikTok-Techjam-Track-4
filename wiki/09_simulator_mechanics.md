# 09 — Customer Simulator & Session Mechanics (Ground Truth)

Everything on this page is read directly from the organizer's actual code
(`external/techjam-conversational-search/evaluator/local_evaluator.py` and
`docs/competition_specification.md`), not inferred — this is the authoritative behavior our agent
is actually evaluated against. Cross-check this page, not memory, when in doubt.

## Session protocol (exact)

1. Evaluator picks a session, calls `agent.reset(session_id, user_profile)`.
2. Turn 1's `user_message` is generated by `initial_message()` (see below) — the agent does not
   choose this, it's the scenario's opening line.
3. Loop turns 1..10: call `agent.respond(session_id, user_message, turn, top_k=10)`.
   - Response is normalized: first 10 unique, catalog-valid `parent_asin` values from
     `recommendations`, in order. Anything else in the response is ignored for scoring except
     `ask_attribute` (drives the next customer reply) and `usage` (feasibility only, not scored).
   - **Malformed response, exception, or timeout ⇒ treated as an empty response for that turn**
     (not a session-ending error) — a crash costs a turn, it doesn't end the session early.
   - If `target parent_asin` is in the returned list **and** (for Intent Override sessions) the
     override has already been delivered ⇒ **hit**. `rank` = 1-indexed position, turn = current
     turn. Loop breaks.
   - If turn == 10 and no hit ⇒ miss (`first_hit_turn = None`, scored as turn 11 for MTTC, 0 for
     reciprocal rank).
   - Otherwise, the next `user_message` is generated (see Customer reply logic below) and the loop
     continues.

## Exact scoring formulas (also on `wiki/00_problem_statement.md`)
```
HitRate@10     = successful sessions / N
MRR            = mean(1/target_rank; misses = 0)
MTTC           = mean(first_hit_turn; misses = 11)
Efficiency     = clip((11 - MTTC) / 10, 0, 1)
TechnicalScore = 0.50 * HitRate@10 + 0.30 * MRR + 0.20 * Efficiency
```
Note: **hits before an Intent Override has fired don't count**, even if the target happens to be in
the ranked list — the session forces the agent through the override.

## Scenario mix (both public and private sets, per `competition_specification.md`)

| Scenario | Share | Turn-1 behavior |
|---|---|---|
| Buying | 40% | Category is stated **and** the first `hard_constraint` is disclosed unprompted: *"I'm looking for {category}. A key requirement is: {constraint}."* |
| Browsing | 40% | Category is stated, nothing else: *"I'm looking for {category}, but I'm still exploring."* |
| Intent Override | 15% | Category + an *old* preference stated turn 1; a forced override message replaces it on turn 3 or 4 **regardless of what the agent asks or does** — this is a scripted turn injection, not conditional on `ask_attribute`. |
| Boundary | 5% | Same as Browsing/Buying opening, but the **first** time the agent asks about *any* attribute, the customer replies "I don't have a preference for X; please use your judgment." once, then behaves normally after. |

**The category is stated in the opening message in every scenario, every session** — derived from
the real target product's actual category tree (`coarse_category()`: last two non-generic category
tokens). This means naive category-string matching from turn 1 is available for free in 100% of
sessions, independent of intent/scenario.

## Customer reply logic (`customer_reply()`, drives turns 2+)

- If the agent's `ask_attribute` is falsy/`None` ⇒ customer says *"Those options are not quite
  right yet. Ask me about one specific attribute."* — **a null `ask_attribute` never reveals new
  information**, it's a wasted turn from an information standpoint (still counts as a turn toward
  the 10-turn cap and MTTC).
- If `ask_attribute` is set: the simulator looks at the session's hidden `intent_card`
  (`hard_constraints` + `soft_preferences`, up to ~4 short strings total, see below) for values
  **not yet disclosed** whose heuristic classification (`classify_constraint()`, below) matches the
  asked attribute. Up to 2 matching, undisclosed values are revealed per turn.
  - No match ⇒ *"I don't have an additional preference for {attribute}."* (wasted turn, but tells
    the agent that bucket is empty — useful only for elimination).
  - Match ⇒ *"For that, what matters is: {value1}; {value2}."* and those values move from hidden to
    disclosed (won't be repeated).

### `classify_constraint()` taxonomy (exact heuristic order — asking off-taxonomy wastes a turn)
1. `budget` — text contains "budget" or a `$`/`<=`/`under` followed by a digit.
2. `material` — one of: cotton, polyester, nylon, leather, wool, spandex, silk, rayon, fabric.
3. `color` — one of: color/black/white/blue/red/pink/green (note: this list is short — many colors
   like "purple"/"yellow" are matched by the earlier `COLOR_RE` used to *seed* the intent card, but
   are **not** in this classifier's own keyword list, so a genuinely purple item's color constraint
   could mis-classify as `feature` — a real corner case worth testing empirically once we build).
4. `size` — size/sizing/width/wide/narrow.
5. `style` — department/style/fit/sleeve/neck.
6. `use_case` — hiking/running/gym/winter/outdoor/work.
7. else ⇒ `feature` (catch-all).

## How the hidden `intent_card` is built (`intent_card()`)
For the target product: candidate list = product `features` + `details` values (flattened), with
a regex-matched **material** keyword inserted at position 0 if found, a **color** keyword inserted
at position 1 (as `"color: X"`) if found, and a **price** string (`"budget around $X"`) appended at
the very end. After de-duplication:
- `hard_constraints = cleaned[:2]` — in practice, almost always **[material, color]** when both are
  found in the corpus, else material + first feature/detail.
- `soft_preferences = cleaned[2:4]`, falling back to `cleaned[:1]` if empty.

**Consequence worth designing around**: because `price`/`budget` is appended *last* to the
candidate list before slicing, it usually falls outside `cleaned[:4]` unless the product has very
few features/details recorded — **asking `ask_attribute: "budget"` will frequently yield "I don't
have an additional preference for budget" even though the target has a real price.** Don't over-
invest in a budget-clarification strategy; verify empirically per-product rather than assuming
price is a reliably obtainable slot from clarification (it's still usable directly for ranking/
filtering since price is a visible catalog field regardless).

## Intent Override mechanics
- Only exists for the 15% `intent_override` scenario.
- The override fires on a scripted turn (3 or 4, chosen once per sample) **unconditionally** — it
  overrides whatever `customer_reply` would otherwise have said, regardless of the agent's
  `ask_attribute` that turn.
- Message format: *"Actually, ignore my earlier preference. What I need is: {new_value}."*, where
  `new_value` is the session's `hard_constraints[0]` (i.e., the override reintroduces the "real"
  hard constraint that Buying-scenario sessions would have gotten on turn 1 — Intent Override
  sessions deliberately start on a wrong/old value and self-correct mid-session).
- The agent **cannot score a hit before the override fires**, even by coincidence — so an agent
  that nails the (wrong, pre-override) preference early gets no credit for it here; it must track
  the override and re-target.

## Agent interface (verified against `docs/competition_specification.md` + `starter/agent.py`)
```python
class Agent:
    def reset(self, session_id: str, user_profile: dict) -> None: ...
    def respond(self, session_id: str, user_message: str, turn: int, top_k: int) -> dict:
        return {
            "message": "...",                 # customer-facing text, informational only for scoring
            "ask_attribute": "material",       # one of the 10 allowed values below, or null
            "recommendations": [{"parent_asin": "B000..."}, ...],  # ranked best→worst, ≤10 scored
            "usage": {"prompt_tokens": 120, "completion_tokens": 30}  # optional, feasibility only
        }
```
`ask_attribute` allowed values: `category, material, color, size, style, brand, budget, feature,
use_case, other, null`. Note `brand` is allowed by the contract but has **no corresponding branch**
in `classify_constraint()` — asking `brand` can never match a constraint via that function (it would
have to fall through to `feature` if `other` isn't used), another concrete gap worth testing rather
than assuming symmetric support across all 10 allowed values.

## Local dev harness vs. final submission format (confirmed — a real gotcha)

- **Local evaluation hardcodes the agent's location.** `evaluator/local_evaluator.py` does
  `from starter.agent import Agent` and instantiates `Agent(args.catalog)` with **no CLI flag to
  point at a different module**. To run `python -m evaluator.local_evaluator` locally, our actual
  implementation must live at (or be imported by) `starter/agent.py`'s `Agent` class — confirmed by
  reading the file directly, not inferred. The README says explicitly: *"Edit `starter/agent.py`
  to implement your system. Do not edit the evaluator or public labels."*
- **The final submission format is different**: `docs/submission_rules.md`'s "Recommended File
  Layout" is a standalone package — `submission/agent.py` + `requirements.txt` + `README.md` +
  `src/` — not `starter/agent.py`. Disallowed: "code that modifies evaluator files."
- **Design implication**: keep the actual implementation in a separate importable module (e.g.
  `src/` or a top-level package), and make `starter/agent.py` (for local dev/eval) and the eventual
  submission's `agent.py` (for final packaging) both thin re-exports of the same `Agent` class —
  avoids duplicating logic across the two required entry points.
- **No numeric resource limits are published.** `docs/submission_rules.md` only says the organizer
  "reserves the right to run your submission under CPU, memory, timeout, and network restrictions"
  — no exact numbers anywhere in the docs. Build defensively (bounded memory/latency by design,
  e.g. capped candidate sizes, no unbounded loops) rather than assuming generous headroom, and
  disclose an offline fallback if any external LLM API is used, since network access may be
  disabled at final judging.
- **Starter agent confirmed** (`starter/agent.py`): stateless SQLite FTS5 BM25 over
  title/categories/features/details/store/description (weighted 6.0/4.0/2.5/2.5/1.5/1.0), top-40
  unique query terms OR-joined, `ask_attribute` always `None` (never clarifies), no cross-turn
  memory. This is exactly why it scores so low — no state, no clarification, pure single-turn BM25.

## Implications to carry into design (flagged now, decided later — see `status.md`)
- Category is free turn-1 signal in 100% of sessions — the retrieval layer should exploit this
  immediately regardless of Buying/Browsing routing.
- Only ~2-4 distinct constraint strings exist per session, ever. Clarification value caps out fast
  — after 2-3 well-classified questions, there's nothing left to learn and further clarification
  turns are pure waste against MTTC.
- `ask_attribute` choice quality is graded against a **specific, inspectable heuristic**
  (`classify_constraint`) we now know exactly — our clarification-attribute selection strategy
  should be built and tested against this real function, not a generic assumption about what
  "material" or "color" means.
- Budget/brand clarification are structurally weak channels (see above) — rely on catalog `price`
  field directly for budget filtering instead of expecting it via clarification.
- Intent Override is not detectable early — it's a scripted turn injection irrespective of agent
  behavior. The dialogue state tracker must be ready to hard-reset on *any* turn's message content
  (the override message itself is the only signal, worded distinctly: "Actually, ignore my earlier
  preference...").
